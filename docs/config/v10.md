# Deskmate application config v10

Status: current, subtractive card-authoring contract. The companion owns this JSON
document; the webview exchanges the same shape through typed IPC but does not read or
write the file directly. The complete UTF-8 document is limited to 65,536 bytes and
unknown fields are rejected at every level.

This document supersedes `docs/config/v9.md`. **v10 removes `playlists` and
`active_playlist_id`: `cards` is ordered, and that order IS the loop.** Dwell moves onto
the card, and `advance` -- timed or manual -- becomes one setting for the whole document.
The card-kind set is unchanged: `clock`, `pomodoro`, `picture`.

The product has exposed exactly one playlist and offered no way to create a second since
the one-loop change of 2026-09-06, so the named grouping described state no surface could
author. Two UI states went with it, both artifacts of keeping two lists rather than
features: a card sitting outside the loop ("not in loop", with its "Add to loop" button),
and a loop position whose card id did not resolve ("Missing card"). Neither is
representable in v10.

**A consequence worth stating plainly:** a card that raised alerts without ever being
shown is no longer expressible. That state required a card to be in the library but
outside the playlist, which nothing in the window could arrange. Every card is in the
loop, so every card is shown.

The wire contract and firmware were unchanged by this schema bump: it was protocol v1
with `PROTOCOL_CURRENT_CAPABILITIES = 2027` throughout. **Protocol v2 followed separately
and touched neither this schema nor the scene map** -- it re-based the capability bits to
`2016` and removed the wire's template model, which this schema had already stopped
describing. Every scene node kind, `VolatileAssets` and `DurableAssetEncoding` remain
supported by the device. The host no longer authors manifest scenes or sends volatile
raster frames.

## Root and stable identity

```json
{
  "schema_version": 10,
  "preferences": {},
  "cards": [],
  "image_sources": [],
  "assets": [],
  "advance": { "kind": "manual" },
  "updater": {}
}
```

Preferences, image sources, assets, playlists, tap actions, refresh policies, and
updater settings keep their v8 shapes and bounds. Card, image-source, asset, and
playlist IDs remain separate namespaces.

**Correction, 2026-09-11:** this paragraph also said templates kept their v8 shape. They
did not for long. `DisplayTemplate` now has exactly three variants --
`digital-clock`, `analog-clock`, `progress-ring` -- because `row-list`,
`big-number-label` and `icon-badge-text` were deleted along with the retired C-template
oracle that was their last consumer. **No valid v9 document changes meaning**: since v8
only clock and pomodoro carry a template at all, and validation already restricted clock
to the two clock templates and pomodoro to `progress-ring`, no document naming one of
the three could ever have validated. A document that names one now fails at
deserialization rather than at composition validation, with a different but still typed
error. The schema version did not move because the set of accepted documents did not.

## Card kinds

Clock and Pomodoro are on-device faces. Their live bindings let time and timer state
continue changing between host pushes:

- `clock` compiles to its authored digital- or analog-clock template;
- `pomodoro` compiles to `progress-ring` and retains its timer actions and
  `on-timer-finish` alert.

Picture is the only server-side face:

```json
{
  "kind": "picture",
  "id": "usage",
  "title": "Claude limits",
  "source_id": "claude-limits",
  "tap_action": { "kind": "none" },
  "refresh": { "kind": "manual" },
  "alert": { "kind": "none" }
}
```

A picture card names a document-level image source. An external producer pushes a
448×368 PNG to that source's token-addressed webhook. The server stores the canonical
RGB565 frame as a durable asset, sends it to the device, and keeps only the latest frame.
The picture is frozen until the next push; server-side cards no longer have device-live
time or timer bindings.

`RefreshPolicy::Interval` remains accepted for Picture for compatibility with the v7/v8
shape and validation rules, although pushed images determine when content changes.

## Migration and compatibility

Every v4-v8 load removes cards whose kind is `calendar`, `weather`, `json-feed`, `rss`,
or `plugin`, then removes every playlist entry naming one of those cards. An inactive
playlist left empty is removed.

The active playlist is never allowed to disappear or remain empty. If all of its entries
were retired, migration adds the same digital clock card `AppConfig::default()` builds
and one entry naming it. The playlist itself is repaired in place, so its id, name, and
pacing survive. Surviving cards, entries, image sources, assets, preferences, and updater
settings are otherwise preserved.

Unknown future schema versions, malformed, truncated, oversized, or invalid documents
remain recoverable typed errors. Source bytes are not rewritten until an explicit save.
The transaction order remains: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay.

## Deployment boundaries

`app_core::CURRENT_SCHEMA_VERSION` in `companion/crates/app-core/src/config.rs` is the
single source constant, now `10`. The server binary and installed companion app each
compile their own copy, so deployment remains ordered:

1. Redeploy the server binary.
2. Rebuild and reinstall Deskmate.app.
3. Only then save a document at schema v10.

Saving before both readers understand v10 produces the typed unsupported-version error;
it is not a firmware or protocol compatibility problem.


## The loop (v10)

`cards` is ordered and that order is the loop order. There is no separate list.

| Field | Type | Bounds |
| --- | --- | --- |
| `cards[].dwell_seconds` | integer or null | 5..=3600 when present; null means "use `advance`'s default" |
| `advance` | tagged | `manual`, or `timed { default_dwell_seconds }` with the same 5..=3600 bound |

`MAX_CARDS` (8) is the only bound on the loop's length; the former `MAX_PLAYLISTS` and
`MAX_PLAYLIST_ENTRIES` (both also 8) are gone, so no bound actually moved.

Every card compiles to both a widget and a screen. Before v10 a card could compile to a
widget with no screen -- that is what an alert-capable card outside the playlist was --
and that shape no longer exists.

### Migration from v4-v9

The active playlist's entries become the leading cards, in entry order, each carrying
that entry's `dwell_seconds`; `advance` is taken from that playlist. **Cards the active
playlist did not name are appended after them, in their original order, so no card is
ever lost** -- that is what a v4-v9 "card library outside the loop" becomes. Playlist
names and every inactive playlist are dropped, which is the only thing this migration
discards and the point of the version.

A document whose cards are all retired kinds ends up with an empty loop, which is
invalid; it receives exactly the fallback card `AppConfig::default()` ships, so the panel
is never left with no face.
