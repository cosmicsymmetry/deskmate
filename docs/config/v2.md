# Deskmate application config v2

Status: frozen as the M4 migration and compatibility boundary. The companion owns this
JSON document; the webview exchanges the same shape through typed IPC but does not read
or write the file directly. The complete UTF-8 document is limited to 65,536 bytes and
unknown top-level, widget, layout, action, or structured variant fields are rejected.

## Root and stable identity

```json
{
  "schema_version": 2,
  "preferences": {},
  "widgets": [],
  "screens": [],
  "assets": [],
  "carousel": {},
  "updater": {}
}
```

Widget, screen, and asset IDs are separate namespaces. IDs are 1..32 UTF-8 bytes and
unique within their namespace. A config contains 1..8 widgets and 1..8 screens. Each
widget is referenced by exactly one screen. Lists retain JSON order; compilation does
not sort or generate IDs, so identical input and revision produce identical protocol
messages.

Preferences contain an IANA `timezone` of at most 64 bytes, booleans `autostart` and
`paused`, and `orientation`, which is either `landscape` (90°) or
`landscape-flipped` (270°). Portrait orientation and on-device rotation gestures are
not part of v1.

## Widgets and composition

Every widget is a tagged object with `kind`, stable `id`, `size`, provider fields,
`template`, `tap_action`, `refresh`, and `interrupt_policy`. Sizes are `full`,
`standard`, and `tile`; titles and labels are at most 64 UTF-8 bytes.

| Widget kind | Provider settings | Allowed templates | Refresh |
|---|---|---|---|
| `clock` | `title`, `show_seconds` | `digital-clock`, `analog-clock`, `big-number-label` | `device-local` |
| `pomodoro` | `label`, `duration_seconds` (`1..86400`) | `progress-ring`, `big-number-label` | `device-local` |
| `calendar` | `title`, file/HTTP(S) `source` (max 2,048 bytes) | `row-list`, `icon-badge-text` | `manual` or interval |
| `weather` | `title`, `location` (1..128 bytes), `units` (`metric`/`imperial`) | `big-number-label`, `icon-badge-text` | `manual` or interval (10..1,440 min) |
| `json-feed` | `title`, HTTP(S) `url`, 1..16 mappings | `big-number-label`, `icon-badge-text`, `row-list` | `manual` or interval |
| `rss` | `title`, HTTP(S) `url`, `max_items` (`1..5`) | `row-list`, `icon-badge-text` | `manual` or interval |

Provider URLs are at most 2,048 bytes, must have an HTTP(S) host, and cannot contain
userinfo/password credentials. JSON mapping field names are 1..32 bytes, unique per
widget, and cannot use the reserved `title`, `stale`, or `error` names. Their bounded
declarative paths are 1..256 bytes. A path is rooted at `$`
and contains at most 16 direct `.name` or `[0]` segments; wildcards, filters, recursive
descent, and executable expressions are not accepted. Interval refresh is 1..1,440
minutes except that weather has a 10-minute floor. Provider work uses a fixed 10-second
request timeout, at most three redirects, and at most 1,048,576 response bytes; these
are host safety limits, not user-overridable settings. See `docs/providers/v1.md` for
the runtime, sanitization, and recurrence contract.

Templates are closed tagged objects. `icon-badge-text` optionally carries
`icon_asset_id`; the reference must resolve to an icon asset. Tap actions are `none`,
`start-pause`, `reset`, `dismiss`, `open-url { url }`, or
`open-application { application_id }`. Timer actions are valid only for pomodoro.
Host URLs are HTTP(S), at most 2,048 bytes. Application IDs are 1..2,048 bytes and may
not contain a slash, backslash, or control character; command strings, arguments,
environment expansion, scripts, and paths have no representation. Interrupt policy is
`disabled` or `enabled`.

## Screens and carousel

A screen has an `id` and a tagged `layout`:

- `single { widget_id }` references one `full` or `standard` widget.
- `dashboard { columns, rows, tiles }` uses a 1x1 through 2x2 grid and contains 2..4
  tiles. Each tile has zero-based `column`/`row`, positive `column_span`/`row_span`,
  must fit wholly inside the grid, must not overlap another tile, and must reference a
  `tile` widget.

`carousel.auto_advance_seconds` is `null` or 5..3,600 seconds. Manual navigation and
the array order remain authoritative regardless of timed advance.

## Assets and updater metadata

At most 16 assets may be declared. Each has a stable ID, a file source of at most 2,048
bytes, `maximum_bytes` in `1..262144`, and either:

- `icon { width, height }`, each dimension `1..128`; or
- `font { pixel_size, glyph_ranges }`, with size `8..96`, 1..16 ascending,
  non-overlapping Unicode-scalar ranges, and at most 512 total glyphs.

The sum of asset budgets is at most 1,048,576 bytes. These limits describe the trusted
host conversion/transfer boundary; transfer and commit semantics are introduced in the
asset task.

Updater settings contain `channel` (`stable`, `beta`, or `manual`) and `checks`
(`disabled` or `notify`). A firmware artifact metadata record is bounded to a 64-byte
version, 64-byte model, `1..1048576` bytes, a 64-hex-character SHA-256, a 64-byte
signing-key ID, and an 88-character padded base64 Ed25519 signature. Artifact bytes are
not stored in the config document.

## Migration and compatibility

The store recognizes every released config version before deserializing its full body:

- v0 and released M3 v1 documents migrate in memory to v2.
- Widget IDs, order, provider values, screen IDs/order, preferences, and the two
  landscape orientations are preserved.
- Migration supplies the corresponding M3 template, action, refresh, interrupt,
  single-screen layout, empty assets, disabled timed advance, and stable update defaults.
- Unknown future schema versions, malformed/truncated/oversized files, and invalid
  migrations return a recoverable typed error. The source bytes are not rewritten and
  the in-memory last-good config remains authoritative.

Schema v2 can represent later M4 features before their wire implementations land.
Compilation currently emits only the proven M3 wire subset. A valid config that needs
dashboard, extended-template, host-action, or asset support returns
`requires-capability` rather than silently degrading it.

The transaction order is fixed: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay. A failure before persistence changes nothing. Atomic persistence
failure preserves the prior file and last-good state. Device replay remains idempotent
and authoritative after a successful save.
