# Deskmate application config v3

Status: frozen as the M4 authoring contract. The companion owns this JSON document; the
webview exchanges the same shape through typed IPC but does not read or write the file
directly. The complete UTF-8 document is limited to 65,536 bytes and unknown top-level,
card, template, action, or structured variant fields are rejected **at every level,
including nested objects** — see "Unknown-field rejection" below for why that requires
more than the derive attribute.

This document supersedes `docs/config/v2.md`. v2's `widgets[]`/`screens[]` split, the
three size classes, and the dashboard grid layout are gone from the authoring model.
See `docs/superpowers/specs/2026-08-06-deskmate-card-model-design.md` for the full
rationale; this file states the resulting contract only.

## Root and stable identity

```json
{
  "schema_version": 3,
  "preferences": {},
  "cards": [],
  "assets": [],
  "carousel": {},
  "updater": {}
}
```

Card and asset IDs are separate namespaces. IDs are 1..32 UTF-8 bytes and unique within
their namespace. A config contains 1..8 cards. There is no screen namespace: list order
in `cards` **is** carousel order, and compilation does not sort or generate identifiers,
so identical input and revision still produce identical protocol messages.

Preferences are unchanged from v2: an IANA `timezone` of at most 64 bytes, booleans
`autostart` and `paused`, and `orientation`, which is either `landscape` (90°) or
`landscape-flipped` (270°). Portrait orientation and on-device rotation gestures are not
part of v1.

## Cards

Every card is a closed tagged object carrying `kind`, a stable `id`, provider fields,
`template`, `tap_action`, `refresh`, `presence`, and `alert`. There is no `size` field:
size classes do not exist in this authoring model. Titles and labels are at most 64
UTF-8 bytes.

```json
{
  "kind": "calendar",
  "id": "upnext",
  "title": "Up next",
  "source": { "kind": "url", "value": "https://example.invalid/cal.ics" },
  "template": { "kind": "row-list" },
  "tap_action": { "kind": "none" },
  "refresh": { "kind": "interval", "minutes": 15 },
  "presence": { "kind": "in-rotation", "dwell_seconds": 30 },
  "alert": {
    "kind": "before-event",
    "lead_minutes": 5,
    "hold": { "kind": "seconds", "value": 60 }
  }
}
```

| Card kind | Provider settings | Allowed templates | Refresh |
|---|---|---|---|
| `clock` | `title`, `show_seconds` | `digital-clock`, `analog-clock` | `device-local` |
| `pomodoro` | `label`, `duration_seconds` (`1..86400`) | `progress-ring` | `device-local` |
| `calendar` | `title`, file/HTTP(S) `source` (max 2,048 bytes) | `row-list` | `manual` or interval |
| `weather` | `title`, `location` (1..128 bytes), `units` (`metric`/`imperial`) | `icon-badge-text`, `big-number-label`, `row-list` | `manual` or interval (10..1,440 min) |
| `json-feed` | `title`, HTTP(S) `url`, 1..16 mappings | `big-number-label`, `icon-badge-text`, `row-list` | `manual` or interval |
| `rss` | `title`, HTTP(S) `url`, `max_items` (`1..5`) | `row-list` | `manual` or interval |

A card kind may use a template only when the provider populates the fields that
template declares (`firmware/main/core/template_fields.c`): a template whose renderable
fields the provider never sends draws its placeholders forever, and every field the
provider does send that the template does not declare inflates the device's
`unknown_field_count` on every refresh. `row-list` stays in weather's set for
compatibility only — `validate()` runs on config **load**, nothing migrates a saved card
to a different template, and weather cards saved before the extended templates shipped
are still on `row-list`. Every `json-feed` field is user-mapped by name, so that kind can
populate any template's declared text fields; the host truncates a mapped value to the
capacity the firmware declares for that field name, and emits every mapped scalar as
text because no template exposes a user-mappable integer or boolean field.

`analog-clock`, `big-number-label`, and `icon-badge-text` are now wire-implemented (M4
Task 3): the firmware declares their field schemas and renders them, gated behind the
`ExtendedTemplates` capability bit (`docs/protocol/v1.md`). The companion's per-kind
default template for a newly added card is: `clock` → `digital-clock`, `pomodoro` →
`progress-ring`, `calendar` and `rss` → `row-list`, `weather` → `icon-badge-text`,
`json-feed` → `big-number-label`. This default only applies when a card is added through
the app; it does not migrate cards already saved in an existing configuration, which keep
whatever template they were authored with.

Provider URLs are at most 2,048 bytes, must have an HTTP(S) host, and cannot contain
userinfo/password credentials. JSON mapping field names are 1..32 bytes, unique per
card, and cannot use the reserved `title`, `stale`, or `error` names. Their bounded
declarative paths are 1..256 bytes. A path is rooted at `$` and contains at most 16
direct `.name` or `[0]` segments; wildcards, filters, recursive descent, and executable
expressions are not accepted. Interval refresh is 1..1,440 minutes except that weather
has a 10-minute floor. Provider work uses a fixed 10-second request timeout, at most
three redirects, and at most 1,048,576 response bytes; these are host safety limits, not
user-overridable settings. See `docs/providers/v1.md` for the runtime, sanitization, and
recurrence contract. The `calendar` card's provider snapshot additionally carries a
`next_start_unix_ms` integer field — the next occurrence's start time, independent of
`display_timezone` — which the `before-event` alert trigger below reads.

Templates are closed tagged objects, unchanged from v2. `icon-badge-text` optionally
carries `icon_asset_id`; the reference must resolve to an icon asset. Tap actions are
`none`, `start-pause`, `reset`, `dismiss`, `open-url { url }`, or
`open-application { application_id }`. Timer actions (`start-pause`, `reset`) are valid
only for a pomodoro card **on the `progress-ring` template**: `widget_model.c` refuses
any widget whose template is not `PROGRESS_RING` while carrying a non-`NONE` tap action,
and `ApplyConfig` validation is all-or-nothing, so one such card would make the device
reject the whole layout. Host
URLs are HTTP(S), at most 2,048 bytes. Application IDs are 1..2,048 bytes and may not
contain a slash, backslash, or control character; command strings, arguments,
environment expansion, scripts, and paths have no representation.

### Presence

`presence` states whether and how a card participates in the rotation.

| Variant | Meaning |
|---|---|
| `in-rotation { dwell_seconds }` | Appears in the carousel. `dwell_seconds` is `null` (inherit the global default) or `5..3600`. |
| `alert-only` | Configured and polled, never in the carousel. Exists solely to take over when its alert fires. |
| `off` | Muted. Not polled, not compiled to the wire, settings preserved. A muted pomodoro's timer does not run. |

### Alerts

`alert` is a closed set validated against the card's kind. Only two v1 sources have real
events, so only two triggers exist.

| Variant | Valid on | Fields |
|---|---|---|
| `none` | any kind | — |
| `on-timer-finish` | `pomodoro` only | `hold` |
| `before-event` | `calendar` only | `lead_minutes` `1..60`, `hold` |

`hold` is `until-dismissed` or `seconds { value: 5..600 }`.

`presence` and `alert` are independent fields: a card can be both in the rotation and
alerting (a calendar read during the loop that also warns before its next event), and
muting a card to `off` preserves its lead time and hold settings rather than discarding
them.

#### Known limitation: `AlertHold::Seconds` cannot clear the physical panel

Under protocol v1 there is no host→device message that dismisses an active interrupt.
Dismissal is device-originated only (`DeviceEvent` action `DismissInterrupt`, fired by an
on-device tap). `ActivateScreen` while an interrupt is active changes the *saved*
underlying carousel screen but the interrupt overlay **remains visible**
(`docs/protocol/v1.md`, `ActivateScreen` section), and firmware's
`show_carousel_screen` is skipped whenever an interrupt is active
(`firmware/main/link/protocol_task.c`). M2 has no automatic interrupt timeout: only a
tap dismisses the active interrupt (`docs/protocol/v1.md`, `TriggerInterrupt` section).

Consequently, a bounded `hold.seconds` only bounds the **host's** outstanding-alert
tracking — it frees the host arbiter's slot for the next alert and re-syncs the host's
saved carousel screen — but it does not clear the panel. The device continues showing
the interrupt overlay until the user taps it. Between the host-side expiry and the next
tap, host and device interrupt state are divergent: the device still expects a
dismissal tap, so a further host-triggered alert can be rejected `Busy` by the device
even though the host arbiter believes its slot is free.

Two resolutions exist and **neither has been chosen**:

1. Amend the design so `hold` is host-side bookkeeping only, and document that a bounded
   alert's on-screen overlay persists until tapped.
2. Add an additive host→device dismissal message to the wire protocol, which requires a
   protocol version bump or additive message, corresponding firmware work, and physical
   verification.

This is an open product decision, not a defect in the current implementation. The
runtime code documents the same limitation at the point it arms the hold deadline
(`companion/crates/app-core/src/runtime.rs`, `arm_alert_hold`).

## Carousel

```json
{ "carousel": { "advance": { "kind": "timed", "default_dwell_seconds": 20 } } }
```

`advance` is `manual` or `timed { default_dwell_seconds: 5..3600 }`. Under `timed`, each
in-rotation card holds for its own `dwell_seconds`, or the default when `null`. Manual
navigation and array order remain authoritative regardless of timed advance. Timed
advance is driven entirely by the host, which sends `ActivateScreen` when a card's dwell
expires; the firmware has no rotation timer of its own.

## Assets and updater settings

Unchanged from v2. At most 16 assets may be declared. Each has a stable ID, a file
source of at most 2,048 bytes, `maximum_bytes` in `1..262144`, and either:

- `icon { width, height }`, each dimension `1..128`; or
- `font { pixel_size, glyph_ranges }`, with size `8..96`, 1..16 ascending,
  non-overlapping Unicode-scalar ranges, and at most 512 total glyphs.

The sum of asset budgets is at most 1,048,576 bytes. These limits describe the trusted
host conversion/transfer boundary; transfer and commit semantics are introduced in the
asset task. Card IDs and asset IDs are separate namespaces: a card and an asset may
share the same ID string without conflict.

Updater settings contain `channel` (`stable`, `beta`, or `manual`) and `checks`
(`disabled` or `notify`).

## Unknown-field rejection

Unknown fields are rejected at every level, including nested objects, as a security
property of the config contract, not a nicety. This is straightforward for plain
structs (`#[serde(deny_unknown_fields)]` works as documented), but **serde's
`deny_unknown_fields` is a silent no-op on internally tagged enums**
(`#[serde(tag = "kind")]`): `{"kind":"alert-only","dwell_seconds":10}` deserializes
successfully under the plain derive even though `dwell_seconds` is not a field of the
`alert-only` variant. Every tagged variant in this schema — `presence`, `alert`,
`hold`, `carousel.advance`, `template`, `tap_action`, `refresh`, provider `source`, and
the card `kind` tag itself — is therefore backed by a hand-written validating
`Deserialize` implementation (`strict_tagged_enum` in
`companion/crates/app-core/src/config.rs`) that checks the field set explicitly rather
than relying on the derive attribute. Nested tagged objects are typed as the public
validating type, not a raw inner type, throughout.

## Compiling cards to the wire

The wire protocol does not change. `ApplyConfig` remains
`{0: revision, 1: widgets, 2: screens, 3: rotation}`, exactly as in v2. Compilation
lowers `cards[]` down to that frozen pair:

- Every `in-rotation` or `alert-only` card emits one widget map with `size_class`
  **pinned to `Full`**. Size classes no longer exist in config, and the host will never
  emit a non-`Full` class again; `docs/protocol/v1.md` documents that the firmware must
  still reject a malformed class from an untrusted host.
- Each `in-rotation` card additionally emits one screen map, in card order, whose
  **screen ID is the card ID**. Widget and screen IDs remain distinct wire namespaces,
  so reusing the same string across both is legal, and compilation still invents no
  identifiers.
- `alert-only` cards emit no screen; they are screenless widgets, which
  `docs/protocol/v1.md` already permits.
- `off` cards emit nothing at all: no widget, no screen, no initial push.

Every existing `ApplyConfig` fixture, including the maximum-capacity fixture, stays
byte-valid, because the compilation target did not move — only the authoring model
feeding it changed.

## Validation rules

Carried forward from v2 unchanged: all string, numeric, URL, path, and count bounds;
closed tagged variants; rejection of unknown fields; and the fixed transaction order of
merge, validate and compile, capability check, atomic persist, runtime replacement, then
queued replay.

New or changed in v3:

1. `cards` contains 1..8 entries with unique IDs (1..32 UTF-8 bytes each).
2. `presence: alert-only` requires `alert` to be a variant other than `none`.
3. `alert` variants must match the card kind: `on-timer-finish` only on `pomodoro`,
   `before-event` only on `calendar`.
4. At least one card must be `in-rotation`. An all-alert or all-muted configuration
   would leave the carousel empty and silently fall back to the standalone clock while
   reporting success.
5. `dwell_seconds` is `null` or `5..3600`; `default_dwell_seconds` is `5..3600`.
6. `lead_minutes` is `1..60`; `hold.seconds` is `5..600`.
7. Timed advance is not capability-gated in v3; the host implements it directly.

## Migration and compatibility

The store recognizes every released config version before deserializing its full body.
v0, released M3 v1, and v2 documents each migrate to v3 directly — v0/v1 do not chain
through an in-memory v2 step, because v0/v1 never had `interrupt_policy` or six card
kinds in the first place. All three paths share the same shape of rule:

- **Order comes from `screens[]`, not `widgets[]`.** The screen array is the carousel
  order the user authored; card order follows it, walking `screens` in order and
  looking up the widget each one names. Each card keeps its widget ID — that ID is what
  `PushData`, `ProviderSnapshot`, and pomodoro runtime state key on — and the screen ID
  is discarded.
- `size` is dropped from every card; size classes have no v3 representation.
- A card migrated from a screen-referenced widget gets
  `presence: in-rotation { dwell_seconds: null }`, inheriting the global default. A
  widget with no referencing screen — which validation should prevent but the on-disk
  format permitted — is preserved rather than silently dropped: it becomes `alert-only`
  when its (historical or explicit) interrupt policy was enabled, and `off` otherwise.
  Orphaned widgets are sorted by ID before being appended, since no screen order exists
  to place them.
- Migration cannot itself produce a rotation-rule violation: every legacy schema
  required each widget to be referenced by exactly one screen, so every card built from
  a screen reference is `in-rotation`. The `alert-only`/`off` orphan handling exists
  only to preserve a legal-on-disk document that validation would already have
  rejected, rather than to satisfy the v3 "at least one in-rotation" rule on its own.

**v2 → v3 alert mapping** (v2 had an explicit `interrupt_policy` field and all six card
kinds): `interrupt_policy: "enabled"` becomes the kind-appropriate alert — pomodoro to
`on-timer-finish` with `until-dismissed`, calendar to `before-event` with 5 minutes and
a 60-second hold — because those are the only two kinds that ever had a trigger that
could fire; the other four kinds become `alert: none` regardless. `"disabled"` always
becomes `alert: none`. `carousel.auto_advance_seconds: N` becomes
`advance: timed { default_dwell_seconds: N }`; `null` becomes `advance: manual`.

**v0/v1 → v3 alert mapping:** v0 and v1 predate `interrupt_policy` and support only
three card kinds (clock, pomodoro, calendar). The historical default — hard-coded by
kind, not read from the document — was interrupts enabled for pomodoro and disabled for
clock and calendar. Migration reproduces that default: pomodoro becomes
`on-timer-finish` with `until-dismissed`; clock and calendar become `alert: none`. A v1
calendar card therefore does **not** gain a `before-event` alert on migration, unlike a
v2 calendar card whose `interrupt_policy` was explicitly `"enabled"`.

Unknown future schema versions, malformed/truncated/oversized files, and invalid
migrations return a recoverable typed error. The source bytes are not rewritten and the
in-memory last-good config remains authoritative.
- No persisted configuration can contain a dashboard layout: v2 rejected dashboard
  composition with `requires-capability` during validation, and validation ran before
  persistence, so no dashboard document has ever reached disk. The v2→v3 migration path
  therefore has no grid case to handle and must not grow one.

The transaction order is fixed: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay. A failure before persistence changes nothing. Atomic persistence
failure preserves the prior file and last-good state. Device replay remains idempotent
and authoritative after a successful save.
