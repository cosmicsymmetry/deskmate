# Deskmate application config v4

Status: **SUPERSEDED by `docs/config/v5.md`, 2026-08-22.** v5 differs from v4 only in
the asset variants: `font { pixel_size, glyph_ranges }` and `icon { width, height }` —
the pre-`tiny_ttf` design where glyphs were baked host-side at a fixed size — are
replaced by `font`, `icon-font { glyphs }`, and `image`, none of which pin a size,
because the device now rasterizes any glyph at any size from a TTF/OTF at runtime.
Nothing else moved: cards, playlists, alerts, tap actions, templates, and updater
settings are unchanged, and so is the frozen protocol-v1 wire contract. Because
`config.rs`'s compile step has always rejected a non-empty `assets` array, no saved
config has ever contained one, so the v4→v5 migration is a version bump with no data
transformation. This file is kept as the historical record of the v4 authoring
contract; `docs/config/v5.md` is current.

Status (v4, historical): frozen as the V1 playlists authoring contract. The companion
owns this JSON document; the webview exchanges the same shape through typed IPC but does
not read or write the file directly. The complete UTF-8 document is limited to 65,536
bytes and unknown top-level, card, playlist, playlist-entry, template, action, or
structured variant fields are rejected **at every level, including nested objects** —
see "Unknown-field rejection" below for why that requires more than the derive
attribute.

This document supersedes schema v3, whose contract document was deleted on
2026-09-11 when the store stopped reading pre-v4 documents. v4 retains the card
library and alert
model, removes each card's `presence` field and the root `carousel`, and adds named
`playlists`, exactly one of which is active. The frozen protocol-v1 wire contract and
firmware are unchanged. See
`docs/superpowers/specs/2026-08-11-deskmate-v1-reset-design.md` for the full rationale;
this file states the resulting contract only.

## Root and stable identity

```json
{
  "schema_version": 4,
  "preferences": {},
  "cards": [],
  "assets": [],
  "playlists": [],
  "active_playlist_id": "my-playlist",
  "updater": {}
}
```

Card, asset, and playlist IDs are separate namespaces. IDs are 1..32 UTF-8 bytes and
unique within their namespace. A config contains 1..8 cards and 1..8 playlists. Cards
form a library; their array order is not rotation order. The active playlist's entry
order is the rotation order, and compilation does not sort those entries or generate
identifiers, so identical input and revision still produce identical protocol
messages.

Preferences are unchanged from v3: an IANA `timezone` of at most 64 bytes, booleans
`autostart` and `paused`, and `orientation`, which is either `landscape` (90°) or
`landscape-flipped` (270°). Portrait orientation and on-device rotation gestures are
not part of v1.

## Cards

Every card is a closed tagged object carrying `kind`, a stable `id`, provider fields,
`template`, `tap_action`, `refresh`, and `alert`. `presence` no longer exists. There is
no `size` field: size classes do not exist in this authoring model. Titles and labels
are at most 64 UTF-8 bytes.

```json
{
  "kind": "calendar",
  "id": "upnext",
  "title": "Up next",
  "source": { "kind": "url", "value": "https://example.invalid/cal.ics" },
  "template": { "kind": "row-list" },
  "tap_action": { "kind": "none" },
  "refresh": { "kind": "interval", "minutes": 15 },
  "alert": {
    "kind": "before-event",
    "lead_minutes": 5,
    "hold": { "kind": "seconds", "value": 60 }
  }
}
```

| Card kind | Provider settings | Allowed templates | Refresh |
|---|---|---|---|
| `clock` | `title`, `show_seconds` | `digital-clock`, `analog-clock` | `device-local` |
| `pomodoro` | `label`, `duration_seconds` (`1..86400`) | `progress-ring` | `device-local` |
| `calendar` | `title`, file/HTTP(S) `source` (max 2,048 bytes) | `row-list` | `manual` or interval |
| `weather` | `title`, `location` (1..128 bytes), `units` (`metric`/`imperial`) | `icon-badge-text`, `big-number-label`, `row-list` | `manual` or interval (10..1,440 min) |
| `json-feed` | `title`, HTTP(S) `url`, 1..16 mappings | `big-number-label`, `icon-badge-text`, `row-list` | `manual` or interval |
| `rss` | `title`, HTTP(S) `url`, `max_items` (`1..5`) | `row-list` | `manual` or interval |

Clock cards still carry `title`, but no clock face renders it: the digital and analog
faces and the standalone fallback screen all draw themselves unlabelled, so the value
serves only to name the card in the companion's library. The field remains on the wire
and is accepted by firmware, which ignores it.

A card kind may use a template only when the provider populates the fields that
template declares (`firmware/main/core/template_fields.c`): a template whose renderable
fields the provider never sends draws its placeholders forever, and every field the
provider does send that the template does not declare inflates the device's
`unknown_field_count` on every refresh. `row-list` stays in weather's set for
compatibility only — `validate()` runs on config **load**, nothing migrates a saved card
to a different template, and weather cards saved before the extended templates shipped
are still on `row-list`. Every `json-feed` field is user-mapped by name, so that kind can
populate any template's declared text fields; the host truncates a mapped value to the
capacity the firmware declares for that field name, and emits every mapped scalar as
text because no template exposes a user-mappable integer or boolean field.

`analog-clock`, `big-number-label`, and `icon-badge-text` are wire-implemented. The
firmware declares their field schemas and renders them, gated behind the
`ExtendedTemplates` capability bit (`docs/protocol/v1.md`). The companion's per-kind
default template for a newly added card is: `clock` → `digital-clock`, `pomodoro` →
`progress-ring`, `calendar` and `rss` → `row-list`, `weather` → `icon-badge-text`, and
`json-feed` → `big-number-label`. This default applies only when a card is added through
the app; it does not migrate cards already saved in an existing configuration.

Provider URLs are at most 2,048 bytes, must have an HTTP(S) host, and cannot contain
userinfo/password credentials. JSON mapping field names are 1..32 bytes, unique per
card, and cannot use the reserved `title`, `stale`, or `error` names. Their bounded
declarative paths are 1..256 bytes. A path is rooted at `$` and contains at most 16
direct `.name` or `[0]` segments; wildcards, filters, recursive descent, and executable
expressions are not accepted. Interval refresh is 1..1,440 minutes except that weather
has a 10-minute floor. Provider work uses a fixed 10-second request timeout, at most
three redirects, and at most 1,048,576 response bytes; these are host safety limits, not
user-overridable settings. See `docs/providers/v1.md` for the runtime, sanitization, and
recurrence contract. The `calendar` card's provider snapshot additionally carries a
`next_start_unix_ms` integer field — the next occurrence's start time, independent of
`display_timezone` — which the `before-event` alert trigger below reads.

Templates are closed tagged objects, unchanged from v3. `icon-badge-text` optionally
carries `icon_asset_id`; the reference must resolve to an icon asset. Tap actions are
`none`, `start-pause`, `reset`, `dismiss`, `open-url { url }`, or
`open-application { application_id }`. Timer actions (`start-pause`, `reset`) are valid
only for a pomodoro card **on the `progress-ring` template**: `widget_model.c` refuses
any widget whose template is not `PROGRESS_RING` while carrying a non-`NONE` tap action,
and `ApplyConfig` validation is all-or-nothing, so one such card would make the device
reject the whole layout. Host URLs are HTTP(S), at most 2,048 bytes. Application IDs are
1..2,048 bytes and may not contain a slash, backslash, or control character; command
strings, arguments, environment expansion, scripts, and paths have no representation.

### Presence removal

`presence` is not part of schema v4 and is rejected as an unknown card field. Its three
v3 concepts are represented without a per-card state:

| v4 state | Meaning |
|---|---|
| Entry in the active playlist | Appears in the rotation and is polled. |
| Alert-capable card outside the active playlist | Polled and compiled as a screenless widget so its alert can take over globally. |
| Library card with no active-playlist entry and no alert | Not polled and not compiled to the wire; all card settings remain editable. |

A card may belong to more than one playlist, but only entries in the selected active
playlist appear in the current rotation. Membership in an inactive playlist does not
by itself cause the card to be compiled or polled.

### Alerts

`alert` stays on the card, never on a playlist. Alerts are global interrupts and fire
regardless of which playlist is active. Only two v1 sources have real events, so only
two triggers exist.

| Variant | Valid on | Fields |
|---|---|---|
| `none` | any kind | — |
| `on-timer-finish` | `pomodoro` only | `hold` |
| `before-event` | `calendar` only | `lead_minutes` `1..60`, `hold` |

`hold` is `until-dismissed` or `seconds { value: 5..600 }`.

#### Known limitation: `AlertHold::Seconds` cannot clear the physical panel

Under protocol v1 there is no host→device message that dismisses an active interrupt.
Dismissal is device-originated only (`DeviceEvent` action `DismissInterrupt`, fired by
an on-device tap). `ActivateScreen` while an interrupt is active changes the *saved*
underlying carousel screen but the interrupt overlay **remains visible**
(`docs/protocol/v1.md`, `ActivateScreen` section), and firmware's
`show_carousel_screen` is skipped whenever an interrupt is active
(`firmware/main/link/protocol_task.c`). M2 has no automatic interrupt timeout: only a
tap dismisses the active interrupt (`docs/protocol/v1.md`, `TriggerInterrupt` section).

Consequently, a bounded `hold.seconds` only bounds the **host's** outstanding-alert
tracking — it frees the host arbiter's slot for the next alert and re-syncs the host's
saved carousel screen — but it does not clear the panel. The device continues showing
the interrupt overlay until the user taps it. Between the host-side expiry and the next
tap, host and device interrupt state are divergent: the device still expects a
dismissal tap, so a further host-triggered alert can be rejected `Busy` by the device
even though the host arbiter believes its slot is free.

`hold` is therefore host-side bookkeeping only and never clears the panel. The overlay
persists until tapped; protocol v1 gains no host-side dismissal message.

## Playlists

```json
{
  "playlists": [
    {
      "id": "my-playlist",
      "name": "My playlist",
      "advance": { "kind": "timed", "default_dwell_seconds": 20 },
      "entries": [
        { "card_id": "clock", "dwell_seconds": null },
        { "card_id": "upnext", "dwell_seconds": 30 }
      ]
    }
  ],
  "active_playlist_id": "my-playlist"
}
```

A config contains 1..8 playlists with unique IDs and unique names. A playlist ID is
1..32 UTF-8 bytes. A name must not be blank and is limited to 48 Unicode characters.
Each playlist contains 1..8 entries. Every `card_id` must resolve to a library card, and
the same card may not appear twice in one playlist; the same card may appear in several
different playlists. `active_playlist_id` must resolve to a playlist, and the active
playlist cannot be empty.

`advance` belongs to each playlist; there is no global `carousel` in v4. It is `manual`
or `timed { default_dwell_seconds: 5..3600 }`. An entry's `dwell_seconds` is `null`
(inherit that playlist's timed default) or `5..3600`. Manual playlists ignore dwell
values while retaining them in the document. Entry order remains authoritative for
manual navigation and timed advance. Timed advance is driven entirely by the host,
which sends `ActivateScreen` when an entry's resolved dwell expires; the firmware has
no rotation timer of its own.

Switching `active_playlist_id` is an ordinary config apply: validate, compile, persist
atomically, replace runtime state, then queue device replay. There is no new wire
message, and device-side playlist switching is outside V1.

## Assets and updater settings

Unchanged from v3. At most 16 assets may be declared. Each has a stable ID, a file
source of at most 2,048 bytes, `maximum_bytes` in `1..262144`, and either:

- `icon { width, height }`, each dimension `1..128`; or
- `font { pixel_size, glyph_ranges }`, with size `8..96`, 1..16 ascending,
  non-overlapping Unicode-scalar ranges, and at most 512 total glyphs.

The sum of asset budgets is at most 1,048,576 bytes. These limits describe the trusted
host conversion/transfer boundary; transfer and commit semantics are introduced in the
asset task. Card IDs and asset IDs are separate namespaces: a card and an asset may
share the same ID string without conflict.

Updater settings contain `channel` (`stable`, `beta`, or `manual`) and `checks`
(`disabled` or `notify`).

## Unknown-field rejection

Unknown fields are rejected at every level, including nested objects, as a security
property of the config contract, not a nicety. This is straightforward for plain
structs (`#[serde(deny_unknown_fields)]` works as documented), but **serde's
`deny_unknown_fields` is a silent no-op on internally tagged enums**
(`#[serde(tag = "kind")]`). Every tagged variant in this schema — `alert`, `hold`,
playlist `advance`, `template`, `tap_action`, `refresh`, provider `source`, and the card
`kind` tag itself — is therefore backed by a hand-written validating `Deserialize`
implementation (`strict_tagged_enum` in
`companion/crates/app-core/src/config.rs`) that checks the field set explicitly rather
than relying on the derive attribute. Nested tagged objects are typed as the public
validating type, not a raw inner type, throughout. `Playlist` and `PlaylistEntry` also
validate their exact field sets explicitly.

## Compiling cards and playlists to the wire

The wire protocol does not change. `ApplyConfig` remains
`{0: revision, 1: widgets, 2: screens, 3: rotation}`, exactly as in v3. Compilation
lowers the card library and active playlist to that frozen pair:

- Active-playlist entries emit one widget and one screen each, in entry order. The
  **screen ID is the card ID**. Widget and screen IDs remain distinct wire namespaces,
  so reusing the same string across both is legal, and compilation invents no IDs.
- Alert-capable cards outside the active playlist emit screenless widgets after the
  active entries, sorted by card ID. This preserves v3's `alert-only` behavior.
- Cards in neither group emit no widget, no screen, and no initial push.
- Every emitted widget has `size_class` **pinned to `Full`**.
- Playlist names, inactive membership, `advance`, and entry dwell never appear on the
  wire. Rotation and dwell remain host-owned.

Every existing `ApplyConfig` fixture, including the maximum-capacity fixture,
re-encodes byte-for-byte identically, because the compilation target did not move —
only the authoring model feeding it changed.

## Validation rules

Carried forward from v3 unchanged: all string, numeric, URL, path, card/asset count,
template compatibility, and capability bounds; closed tagged variants; rejection of
unknown fields; and the fixed save transaction order.

New or changed in v4:

1. `cards` remains a library of 1..8 entries with unique IDs (1..32 UTF-8 bytes each).
2. `playlists` contains 1..8 entries with unique IDs and unique, nonblank names of at
   most 48 characters.
3. Every playlist has 1..8 entries. Each entry references an existing card, and a card
   cannot occur twice in the same playlist. A card may occur in different playlists.
4. `active_playlist_id` resolves to a playlist; its entries define the nonempty active
   rotation.
5. `alert` variants match the card kind: `on-timer-finish` only on `pomodoro`, and
   `before-event` only on `calendar`. An alert is valid outside the active playlist.
6. Entry `dwell_seconds` is `null` or `5..3600`; each timed playlist's
   `default_dwell_seconds` is `5..3600`.
7. `lead_minutes` is `1..60`; `hold.seconds` is `5..600`.
8. Timed advance is not capability-gated; the host implements it directly.

## Migration and compatibility

The store recognizes every released config version before deserializing its full body.
The schema-v3 migration is:

- Cards keep ids and all settings except `presence`.
- Synthesize one playlist, name "My playlist", `advance` taken from the old global
  `carousel`, entries = the `InRotation` cards in array order with their
  `dwell_seconds`. It becomes active.
- `AlertOnly` cards → library, outside the playlist, alert intact (behaviour
  identical).
- `Off` cards → library with `alert` forced to `None`. This is the single lossy
  point: v3 allowed an `Off` card to carry a never-firing alert; preserving it would
  make muted cards start alerting after upgrade. The migration is behaviour-lossless
  and configuration-lossy exactly here, by design.

The synthesized playlist has ID `"my-playlist"` and name `"My playlist"`. If a v3
document has zero `InRotation` cards, migration selects the first card in authored
array order as the sole entry so the result remains valid; that card keeps its migrated
alert. This deterministic repair covers legal-on-disk v3 documents that validation
would not have allowed the app to persist.

*(Amended 2026-09-05: corrected the fallback description to authored array order.)*

v0, released M3 v1, and v2 documents migrate directly to v4 rather than chaining
through serialized intermediate versions. Their existing `screens[]` order determines
card and playlist-entry order: migration walks screens in order, looks up the widget
each names, preserves its widget ID as the card ID, and discards the legacy screen ID
and size. Orphan widgets are preserved outside the synthesized playlist and sorted by
ID. All legacy paths route their derived cards and entries through the same playlist
synthesis helper, producing ID `"my-playlist"`, name `"My playlist"`, and the legacy
carousel's manual/timed advance.

The v2 alert mapping is unchanged: enabled pomodoro interrupts become
`on-timer-finish` with `until-dismissed`; enabled calendar interrupts become
`before-event` with 5 minutes and a 60-second hold; other kinds and disabled policies
become `alert: none`. v0/v1 predate `interrupt_policy`: their historical defaults make
pomodoro `on-timer-finish` with `until-dismissed`, while clock and calendar become
`alert: none`.

Unknown future schema versions (the boundary fixture is `future-v5.json`),
malformed/truncated/oversized files, and invalid migrations return a recoverable typed
error. Source bytes are not rewritten.

### Validation-failure behavior

A syntactically valid saved document that fails domain validation produces the typed
`ValidationFailed` load outcome with its structured validation issues. The invalid
document is not applied, is not installed as last-good, and is left byte-for-byte
untouched. When a genuine last-good config exists, it remains authoritative and the
failed load queues no replacement or device push.

The UI surfaces the exact message **"Your saved settings failed validation and were not
applied"** and lists the issues. If no genuine last-good config exists, the store may
return built-in defaults with `ConfigOrigin::Defaults` for safe in-memory continuity,
but the outcome remains `ValidationFailed`; because a saved file exists,
`has_saved_config` remains true and the app must not label that state as a first run.
Only a truly absent settings file is a clean defaults load with `has_saved_config`
false.

The transaction order is fixed: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay. A failure before persistence changes nothing. Atomic persistence
failure preserves the prior file and last-good state. Device replay remains idempotent
and authoritative after a successful save.
