# Deskmate application config v5

Status: frozen as the asset-store authoring contract. The companion owns this JSON
document; the webview exchanges the same shape through typed IPC but does not read or
write the file directly. The complete UTF-8 document is limited to 65,536 bytes and
unknown top-level, card, playlist, playlist-entry, template, action, or structured
variant fields are rejected **at every level, including nested objects** — see
"Unknown-field rejection" below for why that requires more than the derive attribute.

This document supersedes `docs/config/v4.md`. **v5 differs from v4 only in the asset
variants.** Everything else — cards, the card library, playlists, alerts, tap actions,
templates, preferences, and updater settings — is unchanged from v4. The frozen
protocol-v1 wire contract and firmware are unchanged: `ApplyConfig` still carries no
asset data, and the device-side asset store built in the earlier tasks of this feature
is driven by the server (Task 11), not by anything this schema adds to the wire.

## Why the asset variants changed

v4's asset kinds — `icon { width, height }` and `font { pixel_size, glyph_ranges }` —
encoded a pre-`tiny_ttf` design where glyphs were rasterized once, host-side, at a fixed
pixel size and baked into the transferred asset. The device now rasterizes any glyph at
any size from a TTF/OTF source at runtime, so a config-authored pixel size or a
pre-selected glyph range would be meaningless: nothing on the device or the host ever
reads it. v5 removes both.

**Because `config.rs`'s compile step has, since assets were introduced, always rejected
a non-empty `assets` array with `RequiresCapability`, no saved config has ever contained
an asset.** That rejection is deleted in this change — asset transfer is now
implemented, gated behind capability bit 5 (`CAPABILITY_ASSET_TRANSFER`) — but its
consequence for migration is that v4→v5 is a version bump with no data transformation:
there is no legacy asset shape to convert, because none was ever persisted.

## Root and stable identity

```json
{
  "schema_version": 5,
  "preferences": {},
  "cards": [],
  "assets": [],
  "playlists": [],
  "active_playlist_id": "my-playlist",
  "updater": {}
}
```

Card, asset, and playlist IDs are separate namespaces. IDs are 1..32 UTF-8 bytes and
unique within their namespace. A config contains 1..8 cards and 1..8 playlists. Cards
form a library; their array order is not rotation order. The active playlist's entry
order is the rotation order, and compilation does not sort those entries or generate
identifiers, so identical input and revision still produce identical protocol messages.

Preferences, cards, and playlists are unchanged from v4 — see `docs/config/v4.md` for
their full contract (card kinds, templates, tap actions, alerts, playlist bounds). This
document restates only what changed: the `assets` array.

## Assets

At most 16 assets may be declared. Each has a stable ID (1..32 UTF-8 bytes, its own
namespace — a card and an asset may share the same ID string without conflict), a file
`source` of at most 2,048 bytes, `maximum_bytes` in `1..262144`, and a `kind`:

```json
{
  "id": "inter",
  "source": { "kind": "file", "value": "/Users/example/Fonts/Inter-Regular.ttf" },
  "kind": { "kind": "font" },
  "maximum_bytes": 262144
}
```

| v5 `kind` | Carries | Notes |
| --- | --- | --- |
| `font` | nothing beyond the shared fields | A TTF/OTF text font. No pixel size: the device rasterizes each text node's glyphs at whatever size that node renders at. |
| `icon-font` | `glyphs`: 1..256 `{ name, codepoint }` entries | A TTF/OTF icon font plus a name→codepoint map, so a card can write `icon_asset_id` plus a symbolic name (e.g. `cloud-rain`) instead of the plugin needing to know a raw Unicode codepoint. `name` is 1..64 UTF-8 bytes and unique within the asset; `codepoint` must be a valid Unicode scalar value (not a surrogate, at most `0x10FFFF`). |
| `image` | nothing beyond the shared fields | An LVGL binary image. Conversion from a source image format happens host-side, so the device needs no PNG/JPEG decoder. |

The sum of asset budgets (`maximum_bytes` across all declared assets) is at most
1,048,576 bytes, checked independently of the per-asset `1..262144` bound. A card's
`icon-badge-text` template may reference an asset by `icon_asset_id`; the reference must
resolve to an `icon-font` asset (v4 required an `icon` asset — the kind name changed,
the rule did not).

These limits describe the trusted host conversion/transfer boundary. Transfer and
commit semantics — content-addressed digests, chunking, resumable upload, and release of
digests no longer desired — are the device-side asset store built earlier in this
feature and the server-side reconciliation driver that consumes this schema (Task 11);
this document states the authoring contract only.

Updater settings are unchanged from v4: `channel` (`stable`, `beta`, or `manual`) and
`checks` (`disabled` or `notify`).

## Unknown-field rejection

Unknown fields are rejected at every level, including nested objects, as a security
property of the config contract, not a nicety. This is straightforward for plain structs
(`#[serde(deny_unknown_fields)]` works as documented), but **serde's
`deny_unknown_fields` is a silent no-op on internally tagged enums**
(`#[serde(tag = "kind")]`). Every tagged variant in this schema — `alert`, `hold`,
playlist `advance`, `template`, `tap_action`, `refresh`, provider `source`, the card
`kind` tag itself, and now the asset `kind` tag — is therefore backed by a hand-written
validating `Deserialize` implementation (`strict_tagged_enum` in
`companion/crates/app-core/src/config.rs`) that checks the field set explicitly rather
than relying on the derive attribute. `AssetKind` follows exactly the same pattern as
`DisplayTemplate`: a private `AssetKindInner` mirror type inside `strict_tagged_enum`
carries the real `#[derive(Deserialize)]`, a `ValidatingDeserialize::allowed_fields`
match enumerates each variant's exact field set (`"font" | "image" => &["kind"]`,
`"icon-font" => &["kind", "glyphs"]`), and the public `AssetKind`'s `Deserialize` impl
parses into `serde_json::Value`, validates the field set through that mirror, then
converts to the public type. `IconGlyphMapping` is a plain (non-tagged) struct, so its
own `#[serde(deny_unknown_fields)]` works without a workaround, the same way
`JsonFieldMapping` and v4's `GlyphRange` did. Nested tagged objects are typed as the
public validating type, not a raw inner type, throughout.

## Compiling cards, playlists, and assets to the wire

The wire protocol does not change; `ApplyConfig` remains
`{0: revision, 1: widgets, 2: screens, 3: rotation}`. Compilation of cards and playlists
to that pair is unchanged from v4 (see that document for the full rule set). Compiling
now additionally carries the validated `assets` list through to `CompiledAppConfig`
unchanged (`compile()` no longer returns `RequiresCapability` for a non-empty `assets`
array), so a caller compiling a config can hand `compiled.assets` to the asset-transfer
driver without re-deriving it from the source `AppConfig`. Nothing about `assets` is
encoded onto `ApplyConfig` itself; asset transfer is a separate message flow gated by
`CAPABILITY_ASSET_TRANSFER`.

## Validation rules

Carried forward from v4 unchanged: all card, playlist, template-compatibility,
provider-URL, and capability bounds; closed tagged variants; rejection of unknown
fields; and the fixed save transaction order.

New or changed in v5:

1. An asset's `kind` is `font`, `icon-font`, or `image` — not `icon` or the old `font`
   shape. `font` and `image` carry no fields beyond `kind` itself.
2. `icon-font` carries 1..256 `glyphs` entries, each a unique `name` (1..64 bytes) and a
   Unicode-scalar `codepoint`.
3. `icon-badge-text`'s `icon_asset_id`, when set, must resolve to an `icon-font` asset
   (previously: an `icon` asset).
4. A config declaring assets now compiles successfully (previously: `compile()` always
   returned `RequiresCapability` for any non-empty `assets` array). `required_capabilities()`
   is unchanged: a non-empty `assets` array still requires `CAPABILITY_ASSET_TRANSFER`.

## Migration and compatibility

The store recognizes every released config version before deserializing its full body.

**The schema-v4 migration is a version bump with no data transformation.** Because
`assets` has never been non-empty in a saved v4 config (compile always rejected it), a
v4 document parses directly as the current (v5) `AppConfig` shape — the `assets` array
is empty either way — and migration only rewrites `schema_version` from `4` to `5`.
There is no v4 asset shape to convert; writing a converter for data that cannot exist
would be dead code exercised by nothing. (A hand-edited v4 file that forges a populated
`assets` array in the old `icon`/`font` shape is not a config this app ever saved, and
is not a migration target: it fails to deserialize as v5's `AssetKind` and surfaces as
the ordinary recoverable `InvalidJson` load error, preserving the last-good config.)

The schema-v3 migration is unchanged from v4:

- Cards keep ids and all settings except `presence`.
- Synthesize one playlist, name "My playlist", `advance` taken from the old global
  `carousel`, entries = the `InRotation` cards in array order with their
  `dwell_seconds`. It becomes active.
- `AlertOnly` cards → library, outside the playlist, alert intact (behaviour
  identical).
- `Off` cards → library with `alert` forced to `None`. This is the single lossy point:
  v3 allowed an `Off` card to carry a never-firing alert; preserving it would make muted
  cards start alerting after upgrade. The migration is behaviour-lossless and
  configuration-lossy exactly here, by design.

The synthesized playlist has ID `"my-playlist"` and name `"My playlist"`. If a v3
document has zero `InRotation` cards, migration selects the first card in authored array
order as the sole entry so the result remains valid; that card keeps its migrated alert.

*(Amended 2026-09-05: corrected the fallback description to authored array order.)*

v0, released M3 v1, and v2 documents migrate directly to v5 rather than chaining through
serialized intermediate versions, exactly as they migrated directly to v4 before this
change. Their existing `screens[]` order determines card and playlist-entry order:
migration walks screens in order, looks up the widget each names, preserves its widget
ID as the card ID, and discards the legacy screen ID and size. Orphan widgets are
preserved outside the synthesized playlist and sorted by ID. All legacy paths route
their derived cards and entries through the same playlist synthesis helper, producing ID
`"my-playlist"`, name `"My playlist"`, and the legacy carousel's manual/timed advance.

The v2 alert mapping is unchanged: enabled pomodoro interrupts become `on-timer-finish`
with `until-dismissed`; enabled calendar interrupts become `before-event` with 5 minutes
and a 60-second hold; other kinds and disabled policies become `alert: none`. v0/v1
predate `interrupt_policy`: their historical defaults make pomodoro `on-timer-finish`
with `until-dismissed`, while clock and calendar become `alert: none`.

Unknown future schema versions (the boundary fixture is `future-v6.json`),
malformed/truncated/oversized files, and invalid migrations return a recoverable typed
error. Source bytes are not rewritten.

### Validation-failure behavior

A syntactically valid saved document that fails domain validation produces the typed
`ValidationFailed` load outcome with its structured validation issues. The invalid
document is not applied, is not installed as last-good, and is left byte-for-byte
untouched. When a genuine last-good config exists, it remains authoritative and the
failed load queues no replacement or device push.

The UI surfaces the exact message **"Your saved settings failed validation and were not
applied"** and lists the issues. If no genuine last-good config exists, the store may
return built-in defaults with `ConfigOrigin::Defaults` for safe in-memory continuity,
but the outcome remains `ValidationFailed`; because a saved file exists,
`has_saved_config` remains true and the app must not label that state as a first run.
Only a truly absent settings file is a clean defaults load with `has_saved_config` false.

The transaction order is fixed: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay. A failure before persistence changes nothing. Atomic persistence
failure preserves the prior file and last-good state. Device replay remains idempotent
and authoritative after a successful save.
