# Deskmate application config v6

Status: frozen as the asset-store authoring contract. The companion owns this JSON
document; the webview exchanges the same shape through typed IPC but does not read or
write the file directly. The complete UTF-8 document is limited to 65,536 bytes and
unknown top-level, card, playlist, playlist-entry, template, action, or structured
variant fields are rejected **at every level, including nested objects** — see
"Unknown-field rejection" below for why that requires more than the derive attribute.

This document supersedes `docs/config/v5.md`. **v6 differs from v5 only in the cards
array: it adds a `plugin` card kind.** Everything else — preferences, the six existing
card kinds, assets, playlists, alerts, tap actions, the six built-in templates,
providers, and updater metadata — is unchanged from v5. The frozen protocol-v1 wire
contract and firmware are unchanged: `ApplyConfig` and `PushScene` carry the same shape
they carried under v5, and `PROTOCOL_CURRENT_CAPABILITIES` is untouched by this schema
change. This document does not implement the plugin's runtime behaviour — it only adds
the schema surface a card needs to name one; the manifest format itself is
`docs/plugins/manifest-v1.md`, the server-side data-fetch and render pipeline is a
separate task, and neither is required for this document to be a complete, valid
authoring contract on its own (an authored `plugin` card is simply not renderable until
that pipeline exists, the same way a `weather` card was validly authorable before its
provider existed).

## Why the card kind changed

Every card kind so far pairs a first-party provider (clock, pomodoro, calendar, weather,
a user-mapped JSON feed, or RSS) with one of six hand-written `DisplayTemplate`s compiled
into firmware C, then — since the scene renderer and stage 3a's scene-native rendering —
re-expressed as a host-built scene that reproduces that template pixel for pixel. Adding
a new face to the panel has therefore always meant either writing new provider code, or
choosing among six fixed layouts, or both.

A plugin card breaks that coupling. It names a curated plugin by id; the plugin owns its
own data source and its own declarative node layout (the manifest format), and the
server compiles that manifest — with fetched data bound in — directly to a scene. No
`DisplayTemplate` selection happens for a plugin card, because there is no fixed layout
to select among: the manifest **is** the layout. This is why the `plugin` card kind
carries no `template` field, unlike every other kind.

## Root and stable identity

```json
{
  "schema_version": 6,
  "preferences": {},
  "cards": [],
  "assets": [],
  "playlists": [],
  "active_playlist_id": "my-playlist",
  "updater": {}
}
```

Card, asset, and playlist IDs are separate namespaces. IDs are 1..32 UTF-8 bytes and
unique within their namespace. A config contains 1..8 cards and 1..8 playlists. Cards
form a library; their array order is not rotation order. The active playlist's entry
order is the rotation order, and compilation does not sort those entries or generate
identifiers, so identical input and revision still produce identical protocol messages.

Preferences, assets, playlists, and the six card kinds carried forward from v5 (clock,
pomodoro, calendar, weather, json-feed, rss) are unchanged from v5 — see `docs/config/v5.md`
and `docs/config/v4.md` for their full contract (templates, tap actions, alerts,
playlist bounds, asset variants). This document restates only what changed: the new
`plugin` card kind.

## The `plugin` card kind

```json
{
  "kind": "plugin",
  "id": "aqi",
  "title": "Air quality",
  "plugin_id": "aqi",
  "tap_action": { "kind": "none" },
  "refresh": { "kind": "interval", "minutes": 15 },
  "alert": { "kind": "none" }
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Card id. 1..32 UTF-8 bytes, unique within the config's card namespace — same rule as every other card kind. |
| `title` | string | The card's own label. At most 64 UTF-8 bytes, optional (may be empty). Same field and same bound as every other kind's `title`; a plugin card is named the same way on every surface as any other card (`cardLabel()`/`cardTitle()` in the companion). |
| `plugin_id` | string | Names the curated plugin this card renders. 1..64 UTF-8 bytes, non-empty. Matches the plugin's own manifest `name` field (`plugin::manifest::MAX_NAME_LEN` is 64 bytes; `app-core` mirrors that bound as `MAX_PLUGIN_ID_LEN` rather than importing it — the `plugin` crate depends on `app-core`, so the reverse dependency would be circular). This document does not validate that `plugin_id` resolves to an installed plugin; that is a server-side, deploy-time fact, not a config-authoring-time one — an unresolvable `plugin_id` is a runtime refusal on that card, not a config validation failure, the same way an unreachable weather location is not a config validation failure. |
| `tap_action` | tagged | Same six-variant closed set as every other card kind (`none`, `start-pause`, `reset`, `dismiss`, `open-url`, `open-application`), but `start-pause` and `reset` fail validation on a plugin card — those require a pomodoro provider, and a plugin card is never one — leaving `none`, `dismiss`, `open-url`, and `open-application` as the values that actually validate. |
| `refresh` | tagged | `manual` or `interval { minutes }`, the same two variants every network-backed provider (calendar, weather, json-feed, rss) accepts — **not** `device-local`, which only clock and pomodoro use. `minutes` is bounded the same way: `MIN_CALENDAR_REFRESH_MINUTES..=MAX_CALENDAR_REFRESH_MINUTES` (1..=1440). This is the generic network-provider bound; nothing plugin-specific narrows it further in this document, though a specific plugin's manifest may declare its own `refresh_minutes` as a data-source default (`docs/plugins/manifest-v1.md`) — the two are independent knobs at different layers, the same relationship a weather card's `refresh` has to that provider's own rate limits. |
| `alert` | tagged | Same closed set as every other kind. In practice only `none` validates today: `on-timer-finish` requires a pomodoro card and `before-event` requires a calendar card (`validate_card_behaviour`), and a plugin card is neither. A plugin-triggered alert kind is not part of this schema change. |

**Deliberately absent: `template`.** Every other card kind carries a `template` field
selecting among the six built-in `DisplayTemplate`s. A plugin
card has no such field, because it does not select among built-in layouts — its manifest
**is** its layout, compiled server-side to a scene the same way a built-in template's
scene is host-built. Do not add a `template` field to a plugin card in a future change
without first deciding what it would even mean; today it means nothing, and its absence
is the whole point of the kind.

### Compatibility-check interaction

Every other card kind's `validate()` calls `validate_composition()` with its own
`template` field wrapped as `Some(template)`, which checks two template-shaped rules:
that the provider actually populates the fields the chosen template declares, and that a
`start-pause`/`reset` tap action is paired with the progress-ring template specifically.
A plugin card
has no template, so `validate_composition()` now accepts `template: Option<&DisplayTemplate>`
and a plugin card passes `None`; both template-shaped checks are skipped for `None`, not
approximated. The two checks that do **not** depend on a template — that
`start-pause`/`reset` requires a pomodoro provider, and that the refresh policy is one
the provider kind accepts — still run for a plugin card exactly as for calendar, weather,
json-feed, and rss.

## Unknown-field rejection

Unknown fields are rejected at every level, including nested objects, as a security
property of the config contract, not a nicety. This is straightforward for plain structs
(`#[serde(deny_unknown_fields)]` works as documented), but **serde's
`deny_unknown_fields` is a silent no-op on internally tagged enums**
(`#[serde(tag = "kind")]`). Every tagged variant in this schema — `alert`, `hold`,
playlist `advance`, `template`, `tap_action`, `refresh`, provider `source`, the asset
`kind` tag, and now the card `kind` tag's new `plugin` variant — is therefore backed by
a hand-written validating `Deserialize` implementation (`strict_tagged_enum` in
`companion/crates/app-core/src/config.rs`) that checks the field set explicitly rather
than relying on the derive attribute. `CardSettingsInner`'s `plugin` arm follows exactly
the same pattern as every other card variant: its `allowed_fields` entry is
`["kind", "id", "title", "plugin_id", "tap_action", "refresh", "alert"]` — the field set
above, plus the tag itself, and nothing else. A JSON object naming any other field on a
`plugin` card (including `template`) is rejected, not silently ignored.

## Compiling cards, playlists, and assets to the wire

The wire protocol does not change; `ApplyConfig` remains
`{0: revision, 1: widgets, 2: screens, 3: rotation}`, and `PushScene` (message 19) is
unchanged. A plugin card still compiles to a `WidgetConfig` entry on `ApplyConfig` —
firmware still needs `widget_id`, `size_class`, `tap_action`, and `interrupt_policy` for
it, independent of which mechanism draws its pixels — but its `template: TemplateKind`
byte is inert: stage 3a retired every built-in C template in favour of scenes for every
card, so firmware no longer switches on this field to choose a renderer for **any** card,
plugin or not. `wire_config()` picks `TemplateKind::DigitalClock` for a plugin card
arbitrarily, purely to keep the field populated for tooling that still reads it; do not
read rendering meaning into that value for a plugin card.

A plugin card's actual pixels come from a scene the server compiles from its manifest
plus fetched data and pushes via `PushScene`, the same delivery mechanism every other
card's scene already uses (stage 3a). That compilation is not part of this schema
change — it is the plugin data-fetch and render pipeline, a separate task — so as of
this document, a config containing a `plugin` card is valid and compiles, but the server
has no code path yet that produces a scene for it. `required_device_capabilities()` is
unchanged by this addition: a plugin card's absent `template` does not itself set
`CAPABILITY_EXTENDED_TEMPLATES` (that bit means "uses a built-in template beyond the
three earliest ones," which is not what a plugin card does), and no new capability bit
is introduced or required by this document. `required_device_capabilities()`
(`config.rs`, `AppConfig::required_device_capabilities`) never references
`CAPABILITY_SCENE_RENDER` at all, for a plugin card or any other -- that bit is not a
per-config requirement this function tracks. Every card's actual pixels reach the
device through `PushScene`, which the session layer gates on `CAPABILITY_SCENE_RENDER`
directly (`device::session::ensure_capabilities`, `server::runtime_device`), independent
of config validation. That is *why* a plugin card needs no new bit here: rendering
capability is a connection-level precondition already enforced elsewhere, not something
`required_device_capabilities()` was ever responsible for.

`initial_fields()` — the `PushData` a card gets on first compile, before any provider
result has arrived — is the same three-field shape weather uses: `title`, `stale: true`,
and `error: "Waiting for provider refresh"`. A plugin's actual field set is named by its
own manifest (`field.*` bindings), which this schema does not parse and does not know;
only the housekeeping fields every provider-backed card carries are knowable here. The
server pushes the plugin's real fields once it resolves the manifest and fetches its
first data snapshot.

## Validation rules

Carried forward from v5 unchanged: all card, playlist, template-compatibility,
provider-URL, and capability bounds for the six existing card kinds; closed tagged
variants; rejection of unknown fields; and the fixed save transaction order.

New in v6:

1. A card's `kind` may now be `plugin`, in addition to `clock`, `pomodoro`, `calendar`,
   `weather`, `json-feed`, and `rss`.
2. A `plugin` card's `plugin_id` must be 1..64 UTF-8 bytes and non-empty
   (`validate_identifier`, `MAX_PLUGIN_ID_LEN`). It is not checked against an installed
   plugin registry at config-validation time.
3. A `plugin` card's `tap_action` must not be `start-pause` or `reset` (those require a
   pomodoro provider); its `refresh` must be `manual` or `interval` with `minutes` in
   1..=1440 (not `device-local`); its `alert` is valid only as `none`, because neither
   `on-timer-finish` (pomodoro-only) nor `before-event` (calendar-only) can pair with a
   plugin card. All three rules are the same rules and the same error codes
   (`InvalidComposition`, `OutOfRange`) every other network-backed provider kind already
   produces — nothing plugin-specific was invented for them.
4. A `plugin` card has no `template` field and none is accepted; supplying one is an
   unknown-field rejection, not a silently-ignored extra key.

## Migration and compatibility

The store recognizes every released config version before deserializing its full body.

**The schema-v5 migration is a version bump with no data transformation.** v6 adds
exactly one thing to the schema — the `plugin` card kind, a new variant of the already
internally-tagged `kind` enum on `CardSettings` — and no v5 document could contain it,
because it did not exist yet. Every other type is byte-for-byte the same shape a v5
document already used, so a v5 document parses directly as the current (v6) `AppConfig`
shape and migration only rewrites `schema_version` from `5` to `6`. This is the same
pattern the v4→v5 migration used for the asset-variant reshape.

**The schema-v4 migration is unchanged in mechanism and now targets v6 directly, not
chained through v5.** Because `assets` has never been non-empty in a saved v4 config
(compile always rejected it before v5) and v6 adds nothing a v4 document could have used
either, a v4 document also parses directly as the current `AppConfig` shape; migration
rewrites `schema_version` from `4` straight to `6` in one step.

The schema-v3 migration is unchanged from v4 and v5:

- Cards keep ids and all settings except `presence`.
- Synthesize one playlist, name "My playlist", `advance` taken from the old global
  `carousel`, entries = the `InRotation` cards in array order with their
  `dwell_seconds`. It becomes active.
- `AlertOnly` cards → library, outside the playlist, alert intact (behaviour
  identical).
- `Off` cards → library with `alert` forced to `None`. This is the single lossy point:
  v3 allowed an `Off` card to carry a never-firing alert; preserving it would make muted
  cards start alerting after upgrade. The migration is behaviour-lossless and
  configuration-lossy exactly here, by design.

The synthesized playlist has ID `"my-playlist"` and name `"My playlist"`. If a v3
document has zero `InRotation` cards, migration selects the first card by ID as the sole
entry so the result remains valid; that card keeps its migrated alert.

v0, released M3 v1, and v2 documents migrate directly to v6 rather than chaining through
serialized intermediate versions, exactly as they migrated directly to v5 before this
change. Their existing `screens[]` order determines card and playlist-entry order:
migration walks screens in order, looks up the widget each names, preserves its widget
ID as the card ID, and discards the legacy screen ID and size. Orphan widgets are
preserved outside the synthesized playlist and sorted by ID. All legacy paths route
their derived cards and entries through the same playlist synthesis helper, producing ID
`"my-playlist"`, name `"My playlist"`, and the legacy carousel's manual/timed advance.

The v2 alert mapping is unchanged: enabled pomodoro interrupts become `on-timer-finish`
with `until-dismissed`; enabled calendar interrupts become `before-event` with 5 minutes
and a 60-second hold; other kinds and disabled policies become `alert: none`. v0/v1
predate `interrupt_policy`: their historical defaults make pomodoro `on-timer-finish`
with `until-dismissed`, while clock and calendar become `alert: none`.

Unknown future schema versions (the boundary fixture is `future-v7.json`),
malformed/truncated/oversized files, and invalid migrations return a recoverable typed
error. Source bytes are not rewritten.

### Validation-failure behavior

Unchanged from v5. A syntactically valid saved document that fails domain validation
produces the typed `ValidationFailed` load outcome with its structured validation
issues. The invalid document is not applied, is not installed as last-good, and is left
byte-for-byte untouched. When a genuine last-good config exists, it remains
authoritative and the failed load queues no replacement or device push.

The UI surfaces the exact message **"Your saved settings failed validation and were not
applied"** and lists the issues. If no genuine last-good config exists, the store may
return built-in defaults with `ConfigOrigin::Defaults` for safe in-memory continuity,
but the outcome remains `ValidationFailed`; because a saved file exists,
`has_saved_config` remains true and the app must not label that state as a first run.
Only a truly absent settings file is a clean defaults load with `has_saved_config` false.

The transaction order is fixed: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay. A failure before persistence changes nothing. Atomic persistence
failure preserves the prior file and last-good state. Device replay remains idempotent
and authoritative after a successful save.

## Where `CURRENT_SCHEMA_VERSION` lives

There is exactly one source constant, `app_core::CURRENT_SCHEMA_VERSION` in
`companion/crates/app-core/src/config.rs`, now `6`. The companion app and the server
both consume it through the shared `app-core` crate rather than each carrying their own
copy in source — but the **server is a separately deployed binary**, built and shipped
independently of any given commit (`docs/config/v5.md`'s deploy notes and this repo's
CLAUDE.md both record this). A server still running a build from before this schema
bump has its own compiled-in `CURRENT_SCHEMA_VERSION` of `5`; a v6 config sent to it is
rejected with `schema version 6 is not supported; expected 5` until that server is
redeployed from a commit that includes this change. Redeploying the server after any
schema bump is not optional cleanup; it is part of landing the bump.
