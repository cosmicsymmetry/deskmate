# Deskmate application config v7

Status: superseded by `docs/config/v8.md`. Frozen as the picture-card authoring contract.
The companion owns this JSON
document; the webview exchanges the same shape through typed IPC but does not read or
write the file directly. The complete UTF-8 document is limited to 65,536 bytes and
unknown top-level, card, image-source, playlist, playlist-entry, template, action, or
structured variant fields are rejected at every level.

This document supersedes `docs/config/v6.md`. **v7 is additive:** it adds the
document-level `image_sources` array and the `picture` card kind. Preferences, the seven
v6 card kinds, assets, playlists, alerts, tap actions, built-in templates, providers, and
updater settings are unchanged. The protocol-v1 wire contract and firmware are also
unchanged: a picture card uses the existing durable-asset and scene paths and compiles
to `TemplateKind::DigitalClock` on `ApplyConfig`, like a plugin card. No new capability
bit is required.

## Why the card kind changed

The manifest path makes each server-rendered card pay for an authoring contract,
fixtures, golden frames, and any missing expression-language features. That cost does
not amortise and confines card authoring to this repository.

A picture card separates the face from that machinery. An external producer sends a
PNG to a named source, and one or more cards display the source's durable,
digest-addressed frame. The device already knows how to store that frame and draw a
full-canvas image. Schema v7 only gives the config a way to name the source and the card
that consumes it.

## Root and stable identity

```json
{
  "schema_version": 7,
  "preferences": {},
  "cards": [],
  "image_sources": [],
  "assets": [],
  "playlists": [],
  "active_playlist_id": "my-playlist",
  "updater": {}
}
```

`image_sources` is a document-level peer of `cards`, because a source is reusable by
more than one card. It has `#[serde(default)]`, so a v4, v5, or v6 document that omits
the field still deserializes. Migration supplies an empty array.

Card, image-source, asset, and playlist IDs are separate namespaces. The existing ID
bounds, playlist order, and stable compilation rules are unchanged from v6. Preferences,
assets, playlists, and the seven card kinds carried forward from v6 (`clock`, `pomodoro`,
`calendar`, `weather`, `json-feed`, `rss`, and `plugin`) retain their v6 contract. This
document restates the plugin kind only where its shape explains the picture kind.

## The `plugin` card kind

```json
{
  "kind": "plugin",
  "id": "aqi",
  "title": "Air quality",
  "plugin_id": "aqi",
  "tap_action": { "kind": "none" },
  "refresh": { "kind": "interval", "minutes": 15 },
  "alert": { "kind": "none" }
}
```

The plugin kind is unchanged from v6. It names a curated manifest with `plugin_id` and
carries no `template`, because the manifest owns its layout. Its identifier, title,
tap-action, refresh, and alert bounds remain those in `docs/config/v6.md`.

### Compatibility-check interaction

The v6 compatibility rule is unchanged. A plugin has no built-in template, so
template-shaped composition checks are skipped. Provider-shaped checks still run:
pomodoro-only tap actions do not become valid on a plugin, its refresh remains a
network-provider policy, and its alert variants remain subject to the same provider
compatibility checks as every other card.

## The `picture` card kind

```json
{
  "kind": "picture",
  "id": "usage",
  "title": "Claude limits",
  "source_id": "claude-limits",
  "tap_action": { "kind": "none" },
  "refresh": { "kind": "manual" },
  "alert": { "kind": "none" }
}
```

A picture card mirrors a plugin card field for field, with `source_id` in place of
`plugin_id`:

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Card identity, under the same rule as every other card kind. |
| `title` | string | The owner's words for distinguishing this card. `cardLabel()` returns `Picture`; `cardTitle()` returns this value. |
| `source_id` | string | Names an entry in the document-level `image_sources` array. An unknown value is `ValidationCode::MissingReference`; it never produces a blank card. |
| `tap_action` | tagged | Same field and compatibility rules as a plugin card. Picture-card interactivity is not part of v7. |
| `refresh` | tagged | Same field and compatibility rules as a plugin card. Producer cadence is inferred by the server, not declared here. |
| `alert` | tagged | Same field and compatibility rules as a plugin card. |

**Deliberately absent: `template`.** The source's picture is the face. On the wire,
`wire_config()` fills the existing template byte with `TemplateKind::DigitalClock`, as
it does for a plugin card. That value keeps the unchanged `WidgetConfig` shape populated;
it does not select a picture renderer. The device learns no new card kind, protocol
message, or capability.

Before its source has a frame, a picture card renders the text-only state “Waiting for
the first picture”. Once a frame exists, the server builds the existing full-canvas
image scene around its durable digest.

## Image sources

```json
{
  "image_sources": [
    {
      "id": "claude-limits",
      "name": "Claude limits"
    }
  ]
}
```

An image source contains only `id` and `name`. It is authoring identity shared by cards;
the frame, accepted push history, and token digest live in the server's separate source
store.

**No credential ever appears in the config document.** The server stores only a digest
of a source token and returns the plaintext once when the source is minted. Keeping the
credential out of config prevents a reusable write token from travelling through config
save, migration, and round-trip paths.

`MAX_IMAGE_SOURCES = 8`. Eight canonical frames occupy ~2.6 MB of the 6 MB assets
partition and 8 of the 31 durable digest slots. The bound leaves capacity for the frozen
plugins instead of letting picture sources consume the device-wide keep-set.

## Unknown-field rejection

Unknown fields remain rejected at every level, including nested objects. This is a
security property of the config contract: a misspelled or future field must fail instead
of being silently discarded on save.

The `picture` card accepts exactly `kind`, `id`, `title`, `source_id`, `tap_action`,
`refresh`, and `alert`. A `template`, token, or any other extra field is rejected. An
image-source object accepts exactly `id` and `name`. The internally tagged card enum
continues to use the explicit field-set validation described by v6 rather than relying
on serde's `deny_unknown_fields` behavior for tagged variants.

## Compiling cards, playlists, and assets to the wire

The wire protocol does not change. `ApplyConfig` remains
`{0: revision, 1: widgets, 2: screens, 3: rotation}`, and `PushScene` remains protocol-v1
message 19. A picture card compiles to a normal `WidgetConfig` whose template byte is
`TemplateKind::DigitalClock`, exactly like a plugin card. Firmware receives no picture
card discriminator and needs no new capability bit.

The picture's actual face is a `PushScene` display list containing one full-canvas
`SceneImage`. When stale, the same stale footer used by other faces is added over the
image. The frame is a durable asset, so loop rotation pushes only the small scene naming
an already-resident digest; it does not move the picture again.

The desired durable-asset set is the union of plugin registry assets and every image
source frame. This union is computed as one set because `AssetRelease.digests` is a
device-wide keep-set: omitting a live digest means deleting it.

Picture scenes negotiate `Native` by construction. They have no live bindings, use the
supported image node, and name a durable resident asset. They do not enter the raster
fallback, consume a volatile slot, or inherit its 30-second floor.

## Validation rules

All v6 validation rules for preferences, existing card kinds, assets, playlists,
template compatibility, provider URLs, capability bounds, closed variants, unknown
fields, and save ordering remain in force.

New in v7:

1. The document accepts `image_sources`, defaulting it to `[]` when absent.
2. At most `MAX_IMAGE_SOURCES = 8` sources may be authored. Eight frames use ~2.6 MB
   of the 6 MB assets partition and 8 of 31 durable digest slots, leaving room
   for frozen plugin assets.
3. A card's `kind` may be `picture` and carries the same fields as `plugin`, except that
   `source_id` replaces `plugin_id`.
4. Every picture card's `source_id` must resolve to an authored image source. Failure is
   the typed `ValidationCode::MissingReference`, never a valid card with a blank face.
5. A picture card accepts no `template` and no credential field.

## Migration and compatibility

The v6-to-v7 migration is purely additive. It preserves the document and supplies
`image_sources: []`; it does not rewrite cards. Because the field has `#[serde(default)]`,
v4, v5, and v6 documents parse without it. Older documents follow the migration contract
already recorded in v6 and gain the same empty source array. Their existing cards,
assets, playlists, and settings round-trip unchanged.

Unknown future schema versions, malformed, truncated, oversized, or invalid documents
remain recoverable typed errors. Source bytes are not rewritten.

### Validation-failure behavior

Unchanged from v6. A syntactically valid saved document that fails domain validation
produces the typed `ValidationFailed` load outcome with its structured validation
issues. This includes a picture card whose `source_id` does not resolve. The invalid
document is not applied, is not installed as last-good, and is left byte-for-byte
untouched. A genuine last-good config remains authoritative and the failed load queues
no replacement or device push.

The UI surfaces the exact message “Your saved settings failed validation and were not
applied” and lists the issues. If no genuine last-good config exists, built-in defaults
may provide safe in-memory continuity, but the outcome remains `ValidationFailed` and an
existing saved file is not presented as a first run.

The transaction order remains: merge command-owned preferences, validate and compile,
check connected-device capabilities, atomically persist, replace runtime state, then
queue full replay. A failure before persistence changes nothing. Atomic persistence
failure preserves the prior file and last-good state. Device replay remains idempotent
and authoritative after a successful save.

## Where `CURRENT_SCHEMA_VERSION` lives

There is exactly one source constant, `app_core::CURRENT_SCHEMA_VERSION` in
`companion/crates/app-core/src/config.rs`, now `7`. The companion app and server consume
it through the shared `app-core` crate, but the deployed server binary compiles its own
copy in.

That deployment boundary is load-bearing. Until the server binary is redeployed, every
v7 save is refused with the typed error `schema version 7 is not supported; expected 6`.
Redeploying the server first is part of the schema bump, not cleanup after it.

**And the installed companion app is a second deployment boundary, which is easy to
forget because nothing about it is deployed.** `Deskmate.app` compiles its own copy of the
constant too, so an app built before the bump cannot read a v7 configuration the server
now holds -- it reports the same typed error, and because it never parses the document it
renders no cards, so nothing can be selected or edited. That looks like a broken window
rather than a stale binary, which is exactly why it belongs here.

This was observed on 2026-09-10: the server had been redeployed, the device was on new
firmware, and the only thing left on v6 was the `.app` bundle in `/Applications` from the
day before.

The full order for a schema bump is therefore:

1. Redeploy the **server** binary.
2. Rebuild and reinstall the **companion app**.
3. Only then save a document at the new version.
