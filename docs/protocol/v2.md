# Deskmate wire protocol v2

Status: **frozen**. Protocol v2 is the wire the device speaks as of the legacy-subtraction
Wave C. It supersedes [v1](v1.md), which is retained as the record of what earlier
firmware speaks and what the retired numbers meant. v2 is **not** additive over v1: it
removes message types, map keys, enums, error codes and capability bits, so a v1 host and
a v2 device cannot interoperate. The version byte in the frame envelope is what keeps that
honest — a v1 host's frames are refused with `VersionMismatch` before any payload is read.

`CURRENT_CAPABILITIES` is `4064`. Multi-byte envelope integers are little-endian. CBOR
integers use RFC 8949 deterministic shortest-form encoding; every array and map is
definite-length and every map's keys are in deterministic order.

## 2026-10-02 additive amendment: panel brightness

`v2.3.0-brightness` adds `DisplayBrightness` (bit 11) and optional `ApplyConfig`
key 4. Protocol stays v2. The server gates the key on the capability at both initial
apply and reconnect replay; `v2.2.0-psram` does not advertise it and continues receiving
the previous shape. **No flash-first deploy order is required.** The schema-v11
server must still precede the v11 SPA because the binary owns config validation.
Retired bits 0-4 and ApplyConfig key 2 remain retired.

## What v2 removed, and why

Every removal has one cause: since scene-native rendering (stage 3a, 2026-08-27) the
device has not rendered a card face. A host builds a display list and pushes it; the
device interprets it. The wire nevertheless went on describing templates, size classes,
interrupt policies and a per-template field registry that nothing read.

| Removed | Was | Why it went |
|---|---|---|
| `PushData` (type 5) | a bag of up to 16 named fields, validated against a per-template registry | its only surviving consumer read three keys out of it by name. Type 5 is now `PushTimer`, which states them. |
| `TemplateKind`, `SizeClass`, `InterruptPolicy` | `ApplyConfig` widget fields | all three described how the device should draw a card. It does not draw cards. |
| `ScreenConfig` and `ApplyConfig.screens` | a carousel-order array of `{screen_id, widget_id}` | since config schema v10 a screen id is always the card id, so the array restated the card list. |
| `DeviceEvent.screen_id` (key 3) | a second identifier beside `widget_id` | every producer set both to the same card. |
| `field.<name>` scene bindings | resolved against the device's field bag | there is no field bag. `core/scene_binding.c` no longer parses the prefix, and `protocol::binding_is_valid` refuses it, so a host cannot mint a scene the device would refuse. |
| `ErrorCode::UnknownScreen` (11), `UnsupportedTemplate` (12), `UnsupportedSizeClass` (13) | | nothing can raise them. `UnknownWidget` (10) is renamed `UnknownCard` and keeps its number. |
| capability bits 0-4 | core widgets, config rotation, dashboard layouts, extended templates, host tap actions | all five described template rendering. |

**Retired numbers are never re-issued.** Message types 5 and 10 changed meaning with the
version byte; error codes 11-13 and capability bits 0-4 are permanently dead. A bit's
number is its identity: re-using bit 0 would make a v1 capability word decode as a
plausible v2 one instead of an obviously wrong one. `RETIRED_V1_CAPABILITY_BITS`
(`0b1_1111`) exists in `crates/protocol/src/message.rs` to say so.

## Framing

Unchanged from v1 except the version byte. Each packet is `COBS(decoded) || 00`. Empty
delimiters are ignored. The decoded bytes are:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | wire version (`2`) |
| 1 | 1 | message type |
| 2 | 2 | flags (`0` in v2) |
| 4 | 4 | request ID; responses echo it |
| 8 | 2 | payload length |
| 10 | N | canonical CBOR payload |
| 10+N | 4 | CRC-32C of all preceding decoded bytes |

The maximum decoded frame is 2048 bytes, therefore payloads are at most 2034 bytes and
COBS frames including their delimiter are at most 2058 bytes. A receiver that exceeds the
encoded limit discards through the next zero delimiter, reports one overflow, and then
resumes. Bad COBS, length, CRC, flags, payload, and unsupported-version/type errors must
not poison the following frame. CRC-32C uses the reflected Castagnoli polynomial
`0x82f63b78`, initial/final XOR `0xffffffff`; `"123456789"` hashes to `0xe3069283`.

Host requests use nonzero IDs. A response has the same ID and exactly one of the
documented response types. IDs may wrap, skipping zero. `DeviceEvent` is the sole
unsolicited type and always uses request ID zero; request ID zero on any other type, or a
nonzero ID on `DeviceEvent`, is invalid. The host allows one outstanding request per
connection and times it out after 2000 ms, demultiplexing request-ID-zero events while
that request is in flight.

| 11 | `TriggerInterrupt` | host to device | `Ack` |
| 12 | `DeviceEvent` | device to host, unsolicited | — |
| 13 | `NetworkConfig` | host to device | `Ack` |
| 14 | `FactoryReset` | host to device | `Ack` |

| 17 | `AssetCommit` | host to device | `Ack` |
| 18 | `AssetRelease` | host to device | `Ack` |
| 19 | `PushScene` | host to device | `Ack` |

Request-only and response-only types used in the wrong direction receive
`UnsupportedMessage`. Unknown types do too. A syntactically valid envelope with another
version receives `VersionMismatch`; framing errors without a trustworthy request ID are
discarded.

Types 13 and 14 are gated by capability bit 7 (`Networking`). Types 15-18 are gated by
bit 5 (`AssetTransfer`); `AssetBegin` with `volatile = true` additionally requires bit 9
(`VolatileAssets`), and a non-raw `encoding` on the durable tier additionally requires bit
10 (`DurableAssetEncoding`). Type 19 is gated by bit 8 (`SceneRender`). A host must not
send a gated message to a device that has not advertised its bit.

Content addressing by digest means there is no separate query message and no list to keep
in sync: the host offers a digest via `AssetBegin` and the device's `Ack` reports whether
the bytes are already present.

`PushScene` is dispatched synchronously under the LVGL lock, building the decoded scene
onto a candidate screen before loading it. A refusal answers `Busy` if something else
currently owns the panel (in practice, an OTA takeover) and `InvalidPayload` if the scene
itself could not be rendered. Either refusal leaves whatever is on the panel: a candidate
screen is only loaded once every node and every asset succeeds, so a refused `PushScene`
never blanks the display.

## What the device models

Exactly three things per card, and nothing else:

1. **Its identity and tap meaning**, from `ApplyConfig` — so a tap can be reported with a
   card id and an action the host will recognise.
2. **Its timer**, from `PushTimer` — so `timer.*` scene bindings keep counting down
   between pushes and a local tap can give optimistic feedback with the link down.
3. **Its face**, from `PushScene` — a display list, redrawn on demand.

Anything else a face shows is computed on the host and arrives inside the display list.
That is the whole model, and it is why the field registry could go.

## CBOR payloads

All schema keys are unsigned integer keys. Unknown integer keys are skipped. Duplicate
keys, missing required keys, indefinite items, non-shortest integers, invalid UTF-8,
trailing payload bytes, and wrong types are errors. Receivers cap CBOR recursion at eight
containers so unknown extension values cannot exhaust an embedded task stack.

- `StatusRequest`, `Heartbeat` and `FactoryReset`: empty map `{}` (`a0`).
- `TimeSync`: `{0: unix_seconds, 1: utc_offset_minutes}`. Seconds are in
  `1577836800..4102444800` (2020-01-01 through 2100-01-01 UTC); offset is `-840..840`
  minutes.
- `PushTimer`: `{0: card_id, 1: revision, 2: total_ms, 3: remaining_ms, 4: running}`. All
  five keys are required. `card_id` is 1..32 UTF-8 bytes; `revision` is a nonzero `u32`
  that must be newer than the retained revision; `total_ms` and `remaining_ms` are `u32`
  milliseconds with `remaining_ms <= total_ms`; `running` is a boolean.
- `Ack`: `{0: acknowledged_type}`, optionally with `1: revision` and/or
  `2: already_present`. Revision is present for accepted `PushTimer`, `ApplyConfig` and
  `PushScene` requests and absent for `TimeSync`, `ActivateCard`, `TriggerInterrupt`,
  `NetworkConfig`, `FactoryReset` and all four asset messages. `already_present` is a
  boolean present if and only if `acknowledged_type` is 15 (`AssetBegin`).
- `HeartbeatAck`: `{0: uptime_ms}` (`u64`).
- `Error`: `{0: code, 1: diagnostic}`. Diagnostic text is at most 96 UTF-8 bytes and is
  for humans, not program logic.

Key 9's revision domain is `PushTimer`'s, and it is global across cards for the current
powered device rather than per card: each accepted push must be numerically greater than
key 9 and the last accepted push. A host seeds its next revision from key 9 after every
connect. Rejected pushes do not consume a revision. Revision zero is invalid and wrapping
is not supported within one powered session. Configuration revision (key 20) and
`PushScene` revision are independent domains.

Keys 29, 30, 31 and 32 are omitted rather than encoded empty when there is nothing to
report, and a reader that does not see one treats the device as having none -- with one
caution for key 32: its absence means the image predates the frame pool, never that the
pool is full. Each of these keys is all-or-nothing, so a partial map is a malformed frame
rather than a device with less to say; both codecs refuse one. Secrets never appear
here: keys 24-32 report tier, connectivity, error presence/state, asset store capacity and
memory occupancy only, never a PSK or token value, and an OTA failure reason carries a stage, an error name
or a numeric HTTP status — never the server URL or bearer token.

## Capabilities

The active and maximum protocol versions are both `2`.

| Bit | Name | Meaning |
|---:|---|---|
| 0-4 | — | **retired.** v1's core widgets, config rotation, dashboard layouts, extended templates, host tap actions. Never re-issued. |
| 5 | `AssetTransfer` | `AssetBegin`/`AssetChunk`/`AssetCommit`/`AssetRelease` (15-18), `Ack` key 2, and `StatusResponse` key 31 |
| 6 | `FirmwareUpdate` | verified firmware update transport and `StatusResponse` key 30 |
| 7 | `Networking` | `NetworkConfig` (13), `FactoryReset` (14), and `StatusResponse` keys 24-29 |
| 8 | `SceneRender` | `PushScene` (19) and its `Ack` |
| 9 | `VolatileAssets` | accepts and resolves raw or RGB565-RLE volatile image assets in PSRAM; gates `AssetBegin { volatile: true }` |
| 10 | `DurableAssetEncoding` | honours `AssetBegin`'s `encoding`/`decoded_length` on the durable tier, not only the volatile one |
| 11 | `DisplayBrightness` | accepts optional `ApplyConfig` key 4, raw panel brightness 26..255 |

The brightness build advertises bits 5-11 (`CURRENT_CAPABILITIES` is `4064`). Unknown high
bits are retained in diagnostics and otherwise ignored.

**A configuration can now require exactly one capability, `AssetTransfer`, and only when
it declares assets.** Nothing about a card list is capability-gated any more: rotation is
not a device feature (a scene arrives already laid out for its mounting), and there are no
templates to support. Before an app persists a draft for a connected device it still
compares the compiled requirements with the advertised bits, and a missing bit is a typed
validation error that leaves the draft, runtime state, config revision and device state
unchanged.

A device that does not advertise bit 8 receives its card model — `ApplyConfig` and
`ActivateCard` — and no face. The host records a typed per-card refusal rather than
pushing something the device cannot draw or letting the card go silently blank. There is
no fallback renderer to degrade to.

## `ApplyConfig`

Payload: `{0: revision, 1: cards, 3: rotation}`, optionally with `4: brightness`.

- `revision` is a nonzero `u32` in a configuration-specific revision domain.
- `cards` is an array of 1..8 card maps `{0: card_id, 1: tap_action}`, in carousel order.
  `card_id` is 1..32 UTF-8 bytes and unique within the array.
- `rotation` is `90` for landscape with the USB cable below or `270` for the flipped
  landscape mounting. It is optional and a missing value decodes as `90`. Portrait values
  are rejected.

- `brightness` is an optional unsigned integer raw panel level in `26..255`,
  not a percentage. Missing means retain the current level (200 after normal boot).
  Wrong types, negatives, values below 26 and values above 255 are refused; no
  truncation or wrap is allowed. It is part of semantic replay equality.
  The host sends it only when bit 11 is advertised. UI work is queued to the LVGL
  timer; ACK confirms acceptance, while status key 6 reports the last successful
  board write. A driver failure is logged and retains the previous reported level.
  It is RAM only: reboot starts at 200 and the next host config restores the preference.
  The standalone clock's existing top-half diagnostic remains unchanged.

**Key 2 is retired**, not renumbered: it carried v1's `screens` array. `rotation` keeps
key 3. Renumbering would make a v1 `ApplyConfig` decode as a plausible v2 one.

The device validates the complete candidate before changing live state. A higher revision
atomically replaces the prior config. The same revision with a semantically identical
config is an idempotent replay and is acknowledged; the same revision with different
content, or a lower revision, receives `StaleRevision`. A rejected config does not change
the live model, revision, active card, or interrupt state. An accepted replacement
preserves the active card when that id still exists, otherwise selects the first card; it
clears active and pending interrupts without emitting dismissal events. The `Ack` echoes
type 9 and the accepted config revision.

Wire semantic validation is in
`firmware/main/core/apply_config_validation.h`: a nonzero revision and a non-empty card
list, a rotation of 90 or 270, optional brightness in 26..255, and a non-empty unique `card_id` with a `tap_action` in
range for every card. Everything v1 checked beyond that asked whether the device could
*render* a card.

`StatusResponse` key 20 is the connect-time config handshake. A reconnecting host may skip
an already-applied revision or replay it idempotently.

| Registry | Value | Name | Rule |
|---|---:|---|---|
| tap action | 0 | `None` | valid for every card |
| tap action | 1 | `StartPause` | acts on the card's timer |
| tap action | 2 | `Reset` | acts on the card's timer |
| event kind | 1 | `Tap` | action is `StartPause` or `Reset` |
| event kind | 2 | `Navigation` | action is `NavigatePrevious` or `NavigateNext` |
| event kind | 3 | `InterruptDismissed` | action is `DismissInterrupt`, token required |
| event action | 0 | `None` | config-side sentinel; invalid in `DeviceEvent` |
| event action | 1 | `StartPause` | card tap |
| event action | 2 | `Reset` | card tap |
| event action | 3 | `NavigatePrevious` | local swipe selected the previous card |
| event action | 4 | `NavigateNext` | local swipe selected the next card |
| event action | 5 | `DismissInterrupt` | active interrupt was dismissed |

A tap action naming a card with no timer is accepted by the wire and simply produces an
event the host may ignore: the device does not know which cards have timers until one is
pushed, and refusing the config for it would make card order and timer arrival
order-dependent.

## `ActivateCard`

Payload: `{0: card_id}`. The selected card must exist in the current config. The operation
is idempotent and does not change carousel order. Unknown IDs receive `UnknownCard`;
success returns `Ack` for type 10 without a revision. While a priority interrupt is
active, activation changes the saved underlying carousel card; the interrupt remains
visible and dismissal restores the newly selected card.

## `TriggerInterrupt`

Payload: `{0: card_id, 1: token, 2: reason}`. The card must exist. Tokens are nonzero
`u32` values, strictly increasing among accepted nonduplicate triggers. Reasons are 0..96
UTF-8 bytes. A token already present in the active or pending slot is an idempotent replay
and is acknowledged only when card and reason are also identical. Reusing that token with
different content, or sending an older token, receives `StaleRevision`.

v1 gated this on the widget's `InterruptPolicy`. There is no policy on the wire any more:
whether a card may interrupt is a host decision, expressed by whether the host sends one.

The first accepted trigger becomes active and saves the exact carousel card. While one
interrupt is active, one newer trigger may occupy a FIFO pending slot. A further new token
receives `Busy` and is not consumed, so it may be retried after space opens. Dismissal
emits one event for the active token, then promotes the pending slot or restores the saved
carousel card. Success returns `Ack` for type 11 without a revision. There is no automatic
interrupt timeout: a tap dismisses the active interrupt, and host loss temporarily replaces
all host content with the standalone clock without discarding the interrupt slots.

## `DeviceEvent`

Payload: `{0: sequence, 1: event_kind, 2: card_id, 4: action}`, or the same map with
`{5: interrupt_token}`. Keys 0, 1, 2 and 4 are required. Key 5 is required only for
`InterruptDismissed` and forbidden for other event kinds. **Key 3 is retired** — it
carried v1's second identifier — and is not re-used. `sequence` is a nonzero `u64`.

`card_id` names the card the event is about: the card tapped, the card navigated to, or,
for a dismissal, the saved carousel card that will be restored after pending-interrupt
promotion completes.

Delivery is at-most-once: events are not acknowledged or retransmitted. The device assigns
sequence numbers when enqueueing, increments them monotonically from one, and drops the
newest event if the bounded event queue is full. A gap lets the host detect loss but not
recover the event. Duplicate or out-of-order events are ignored by the host. The next
authoritative `PushTimer` reconciles any optimistic local tap feedback.

## Local gesture and animation semantics

LVGL supplies points in the current logical 448x368 landscape coordinate system for both
90- and 270-degree display rotations. A tap lasts at most 500 ms and moves no more than 18
pixels on either axis. A horizontal swipe lasts at most 750 ms, moves at least
`max(56, logical_width / 6)` pixels on the primary axis (74 pixels at 448 wide), and its
horizontal displacement is at least 1.5 times its vertical displacement. A left swipe
selects next; a right swipe selects previous. Other releases emit no event.

Orientation has no local touch gesture. The companion owns the two landscape mounting
choices through `ApplyConfig`, and the device keeps that orientation when it falls back to
the standalone clock until a later config or reboot changes it.

A pushed timer is an authoritative snapshot. While `running` is true, firmware advances it
from that snapshot on a 250 ms LVGL timer using a monotonic tick; no per-frame host push is
required, which is what keeps a `timer.*` binding counting down with the link gone.
Start/pause/reset taps apply bounded optimistic visual feedback immediately. The next
complete `PushTimer` always replaces that local feedback, including after an event was
dropped under pressure.

## `NetworkConfig`

`{1: ssid, 2: psk, 3: server_url, 4: device_id, 5: token, 6: utc_offset_minutes,
7: tier}`. All seven keys are required; keys start at 1 (not 0). `ssid` is 0..32 UTF-8
bytes, `psk` is 0..64, `server_url` is 0..128, `device_id` is 0..32, `token` is 0..128;
`utc_offset_minutes` reuses the `TimeSync` bound (`-840..840`); `tier` is `0` (local) or
`1` (networked). Unlike every other message in this registry, an unrecognized key inside
the map is rejected rather than skipped: this is a closed, credential-carrying schema, not
an additive one. Secrets travel down only — `StatusResponse` never echoes a PSK or token
value back.

## Asset transfer

Unchanged from v1.

- `AssetBegin`:

  | Key | Field | Presence and meaning |
  |---:|---|---|
  | 0 | `digest` | required 32-byte SHA-256 `bstr` of the decoded asset blob |
  | 1 | `kind` | required: `1` (`Font`), `2` (`IconFont`), or `3` (`Image`) |
  | 2 | `total_length` | required `u32` in `1..1048576`; the wire length addressed by every `AssetChunk` offset and by `AssetCommit` |
  | 3 | `volatile` | boolean; always emitted (deployed decoders require the key) |
  | 4 | `encoding` | optional `u8`, default raw (`0`); RGB565 RLE is `1`, and unknown values are refused |
  | 5 | `decoded_length` | optional `u32`; required if and only if `encoding != 0` |

  The device replies with `Ack` carrying `already_present`. A non-raw encoding on the
  durable tier requires bit 10. When `volatile` is true, bit 9 is also required and `kind`
  must be `Image`. The decoded form of a volatile image is exactly 329,740 bytes: a
  canonical 12-byte little-endian LVGL image header (`magic = 0x19`,
  `cf = RGB565 = 0x12`, width 448, height 368, stride 896, all flags/reserved bytes zero)
  followed by 448×368×2 RGB565 bytes. RLE encoding sends that header unchanged, followed
  by `(u16 count LE, u16 pixel LE)` runs; key 5 must then be the decoded length, key 2
  remains the encoded wire length, and an encoding that does not shrink the blob is refused
  in favour of the legal raw form. The SHA-256 digest always addresses decoded bytes, so
  scene references do not depend on the wire encoding. The device holds at most **sixteen**
  decoded PSRAM allocations: fifteen resident frames and one incoming atomic replacement.
  The host learns the true figure from key 32 rather than assuming it, because the capacity
  is a property of the running image and not of this contract -- a fleet mid-rollout reports
  both 2 and 16. A device that cannot reserve a slot answers `AssetBegin` with `Busy` and
  the diagnostic `volatile asset reserve failed`; that is not new behaviour, it is what
  every deployed image has always done, and a host that grows its staging must handle it.
  It never downgrades a volatile transfer to flash.
- `AssetChunk`: `{0: digest, 1: offset, 2: data}`. All three keys are required. `data` is
  a `bstr` of at most 1920 bytes — deliberately short of the 2034-byte envelope cap,
  because the map header, the 32-byte digest with its `bstr` header, the offset key/value
  and the data `bstr` header cost roughly 46 bytes.
- `AssetCommit`: `{0: digest}`.
- `AssetRelease`: `{0: [digest, ...]}` — an array of 0..32 digests forming the complete
  **keep-set** across durable and volatile tiers. Every committed digest absent from the
  array may be reclaimed; an empty array therefore means "release everything", not
  "release nothing".

## `PushScene` and the scene map

`PushScene`: `{0: card_id, 1: revision, 2: scene}`. All three keys are required. `card_id`
is 1..32 UTF-8 bytes; `revision` is a nonzero `u32`. `scene` is a nested map, not a payload
of its own. A `PushScene` replaces whatever the named card was drawing.

The scene map is **unchanged from v1 in every respect but one: the `field.<name>` binding
is gone.** Rather than restate it, [v1's "The scene map" section](v1.md#the-scene-map) is
the reference for node kinds, keys, defaults, bounds, geometry conventions, clipping,
baselines and label anchoring. The one change:

> A `binding` (and an `Arc`'s `end_binding`) is drawn from a closed set the device
> evaluates locally. The grammar is exactly: `date`; `timer.pct`; `timer.permille`;
> `timer.status`; `time:<fmt>`; `timer.remaining:<fmt>`; `timer.elapsed:<fmt>`; and
> `timer.total:<fmt>`. **`field.<name>` is not in the set**, in either implementation: the
> device has no field bag to resolve it against, `core/scene_binding.c` has no
> `SCENE_BINDING_FIELD`, and `protocol::binding_is_valid` refuses the prefix so a host
> cannot mint a scene that would be refused at the far end. A scene naming any other
> binding is refused whole at decode.

Everything a face needs beyond that closed set is computed on the host and arrives in the
display list as a literal. The rule that made `field.*` unnecessary is the same one that
made `PushData` unnecessary: anything computed happens on the host.

Codes 11-13 are retired with the concepts that raised them and are never re-issued.
Duplicate identifiers, invalid enum combinations, bad field types and other schema
violations use `InvalidPayload`. `ConfigTooLarge` covers a validly framed `ApplyConfig`
whose card count exceeds the frozen capacity; a payload that cannot fit the 2034-byte
envelope is rejected by framing before semantic dispatch. `WrongTier` is returned when a
message is valid but not permitted on the transport the device is currently reachable over
for its tier.

## Liveness and state

Boot state is standalone. Every valid request, including heartbeat, changes state to
online and refreshes a 10,000 ms deadline. Invalid traffic never refreshes it. Expiry
returns to standalone, restores the clock connection hint, and leaves the last valid time
and pushed timer intact. The device stores UTC; rendering adds the fixed signed offset
supplied by the latest valid `TimeSync`.

## Golden fixtures

`protocol/fixtures/v2` contains complete wire frames and invalid parser inputs.
`protocol/fixtures/v1` is **retained**, unmodified, as the record of what flashed devices
speak. Regenerate the v2 corpus deterministically from the Rust source with:

```sh
cd companion
cargo run -p protocol --example generate-fixtures -- ../protocol/fixtures/v2
cargo test -p protocol
```
